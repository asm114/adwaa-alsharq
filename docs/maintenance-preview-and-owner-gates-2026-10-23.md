## تجربة iPad التي ينفذها المالك

1. افتح الرابط الافتراضي في Safari على iPad، وأدخل عبارة اختبار من 12 حرفًا ثم ابدأ الجلسة.
2. اربط Drive الوهمي، ثم أنشئ نسخة. جرّب مربع فشل سجل Supabase ومربع انقطاع Drive كلًا على حدة، ثم ضياع رد Drive وإعادة رفع النسخة نفسها. لا ينبغي أن يتضاعف عدد ملفات المحاكاة.
3. اختبر تنزيل JSON ومشاركته إلى «الملفات»، وإلغاء المشاركة، وإرشادات فتح التنزيلات، والوضعين الرأسي والأفقي ولوحة المفاتيح. تحقق بنفسك من وجود الملف؛ الصفحة لا تدّعي تأكيد حفظ لم تره.
4. سجّل النتيجة وموديل الجهاز وإصدار iPadOS دون إرسال رموز أو ملفات العملاء. نجاح WebKit في Linux لا يغلق هذه الخطوة.

## ما يحتاج المالك لتجربة Google الحقيقية

- أنشئ **Web OAuth client تجريبيًا منفصلًا**، واسمح بأصل JavaScript الدقيق `https://adwaa-pr164-isolated-20261023-me8grx12u-asm114-6247s-projects.vercel.app`، بعد إعداد Client ID وإعادة نشر معاينة Preview، اعتمد أصل رابطها النهائي الدقيق إذا تغير، وأضف حساب الاختبار إلى مستخدمي شاشة الموافقة عند الحاجة. الصلاحية المطلوبة `drive.file` فقط. لا توسع أصول عميل الإنتاج ولا ترسل client secret أو access/refresh token.
- أتح فقط **Client ID العام التجريبي** لإعداد المعاينة. أمر البناء يدعم `--google-client-id ID.apps.googleusercontent.com` ويرفض Client ID الإنتاجي. إعادة بناء/نشر مشروع الاختبار فقط مطلوبة لتفعيله؛ الموقع الرئيسي مستقل.
- بعدها اختبر `/live/` بنفسك بملفات المعاينة المصطنعة. هذا ما يتحقق من نافذة Google وسياسة أصل OAuth وSafari وDrive الحقيقي؛ خدمات وهمية أو اتصال Google Drive الخاص بالمساعد ليست بديلًا عنه.

## صلاحيات Supabase — حالة القراءة الفعلية

أعيد فحص الكتالوج فقط دون صفوف الحجوزات أو الأرصدة: ما زالت TRUNCATE وMAINTAIN متاحة لـauthenticated على app_state، ولـanon/authenticated على reservations وpayments. العرض reservation_financials مملوك لـpostgres دون security_invoker. تنبيها العرض وحماية كلمات المرور المسربة ما زالا ظاهرين.

كذلك أكدت pg_default_acl منحًا واسعة للكائنات الجديدة التي ينشئها postgres أو supabase_admin في public، بما فيها EXECUTE للدوال. هذا يفسر خطر عودة المنح عند إنشاء كائنات مستقبلية، لكنه **لا يثبت تاريخ إعادة منح app_state** لأن الهجرة الموجودة تسحب بعض المنح صراحة. لا تُغير default privileges عالميًا دون حصر أثرها على بقية الكائنات واعتماد المالك.

أُضيفت منح افتراضية مماثلة إلى اختبار PostgreSQL المصطنع؛ يُتحقق أن RPC الجديدة تسحب EXECUTE من anon رغم وراثته عند الإنشاء. التصحيح المقترح للأمان ما زال غير مطبق في الإنتاج.

## النسخة الكاملة: ليست ملف JSON للتطبيق

ملف Drive/JSON يغطي بيانات التطبيق التي يصدّرها، ولا يغطي وحده قاعدة Supabase وصلاحياتها وAuth وملفات Storage وإعدادات الخدمات.

على المالك/المشغّل المخول توفير الدليل التالي داخل بيئة محمية، دون إدخال ملفات الإنتاج في المعاينة أو GitHub:

1. فهرس نسخ مشروع `pgdvlklpyrvmwzitsmbw` الحقيقي أو نافذة PITR، وتاريخ/حالة نقطة الاسترداد وRPO مقبول. أداة metadata الموجودة لا تزال تعيد `management_access_token_missing`؛ لا وجود نسخة أو غيابها مثبت بهذه الجلسة.
2. وجهة استعادة مستقلة معتمدة تختلف عن المصدر، مع اعتماد التكلفة قبل إنشائها. الاستعادة إلى المصدر أو تشغيل restore_project عليه ليست اختبارًا مقبولًا.
3. استعادة قاعدة كاملة عبر الوسيلة المدعومة، ومراجعة الجداول/المخططات/الأدوار وRLS والدوال والعروض والتسلسل وبيانات Auth. أسرار وأصول OAuth وإعدادات Auth وEdge Functions وRealtime والامتدادات قد تحتاج إعدادًا منفصلًا؛ كلمات مرور الأدوار الخاصة لا تُفترض محفوظة.
4. فهرس ونسخ ملفات Storage نفسها والتحقق من سلامتها وإتاحتها، لا metadata فقط. النسخ الفيزيائية لقاعدة البيانات لا تعيد الملفات المحذوفة من Storage.
5. عزل cron/webhooks/pg_net والإرسال الخارجي على هدف الاستعادة قبل تشغيل خدماته. لا يُسمح للاختبار بإرسال رسائل أو إعادة مزامنة أنظمة الإنتاج.
6. توثيق نقطة المقارنة الزمنية، ومقارنة أعداد السجلات والبصمات والإجماليات والصلاحيات داخل البيئة المحمية. اختلاف نسخة أقدم عن مصدر واصل استقبال حجوزات ليس سببًا لتغيير المصدر؛ يلزم checkpoint متفق عليه وتقرير RPO.
7. الاحتفاظ بمعرف النسخة وتاريخ الاستعادة وهوية الهدف ونتيجة الاختبار وبصمات الملفات، دون محتوى العملاء أو أسرار. لا يُغلق gate بناءً على عبارة «النسخ مفعّل» أو نجاح JSON محلي.

المتاح والمختبر الآن: pg_dump/pg_restore لقاعدة مصطنعة، وتطابق بياناتها وACL، وانتقال RPC والتراجع الآمن. لا يُسجل ذلك كاستعادة إنتاج.

## ترتيب الأجهزة القديمة والقرار الإنتاجي

الترتيب ما زال: استرداد إنتاج مثبت → اعتماد تصحيح صلاحيات الجداول والعرض → تحضير RPC مع بقاء CAS المباشر → اعتماد الواجهة في بيئة اختبار مستقلة → نشر مصرح → حفظ مسودات وحصر/تحديث جميع الأجهزة والتبويبات وPWA → اعتماد فرض RPC → تحقق مراقب.

اختبار تعايش PATCH وRPC يخص **PATCH المشروط بالإصدار**؛ لا يثبت أمان عميل قديم غير مشروط. لا يمكن قبول كتابة عميل بلا إصدار وضمان منع التعارض في الوقت نفسه. يلزم مالك يعرف الأجهزة المصرح لها ويعتمد نافذة الانتقال؛ إذا تعذر حصرها يبقى المانع مفتوحًا. لا تحديث خفي أو مسح مسودات لفرض الانتقال.

عند تعثر الانتقال، التراجع المختبر يعيد صلاحيات CAS الثلاث فقط ويبقي حماية العرض؛ لا يعيد TRUNCATE أو عرض البيانات لغير المخولين، ولا يستبدل بيانات جديدة بنسخة قديمة. لا يُطبق SQL الإنتاجي قبل بوابة النسخة وموافقة المالك.
