أو سكربت الإعداد. لا تشغيل من main أو timer أو fork. يُثبّت checkout على
SHA حدث push نفسه ويقارنه في runtime. اعتماد هذا SHA يكون بمراجعة التشغيل
في Environment `production-backup` ذات المراجع الإلزامي الموجود؛ لا نغير
الحماية أو متغيرات SHA للمسارات السابقة، ولا نعيد استخدامها لتفويض كود مختلف.
لا يحتاج هذا المسار تحديث repository variables الذي ترفضه صلاحية التكامل.

أُنشئ المجلدان في التشغيل 40315914121، ثم توقف فحص PostgreSQL قبل أي نسخ.
بعد موافقة المراجع الآن: فحص المجلد الخاص المعلّم الموجود لكل مشروع بواسطة
`inspection_report` فقط؛ يتوقف عند غياب المجلد أو تعدده ولا يستدعي الإنشاء.
لا تبني أسماء المجلدات القديمة ولا تُنقل ملفاتها.

والهوية والسعة)، وجرد Storage من SQL ومقارنة buckets عبر GET API الرسمي.
لا تنزيل كائنات أو dump أو تشفير أو استعادة أو حذف في هذه المرحلة.

التقرير لا يحتوي بيانات العملاء أو أسماء الكائنات أو بيانات الاتصال: فقط
folder_id، حجم قاعدة البيانات وإجمالي Storage وأعداد الملفات والحاويات
وإصدارات الإضافات، وحالة إعداد صورة الاستعادة وتقدير الحجم. يحفظ معرف المجلد
في log فور نجاحه وفي Step Summary حتى لو فشل فحص المصدر؛ تُعاد الاستفادة منه
بهوية المشروع عند إعادة التشغيل، دون محاولة إنشاء أخرى.

المرحلة التالية تُجهّز بعد قراءة هذه القياسات: صورة استعادة مثبتة digest
متوافقة مع الإضافات الحقيقية، ميزانية وسعة runner/Drive، ثم نسخة مشفرة كاملة
باستخدام المحرك الحالي وتنزيلها واختبارها داخل Docker network=none. لا تعتمد
صورة postgres العامة دون دليل توافق إضافات Supabase. يلزم كذلك اختبار استرداد
Storage بخدمته الرسمية المعزولة؛ استعادة بايتات TAR وحدها ليست دليل تشغيل API.

استبدال Client Secret المكشوف بوابة قبل اعتماد اليومي. راجع خطة الاستبدال
في tools/backup/windows/README.md: لا تعطّل السر القديم قبل اختبار البديل إن
سمح Google بتداخل الأسرار، ولا تغيّر مفاتيح تشفير النسخ أو كلمات مرور PG.

## تشخيص PostgreSQL دون كشف الأسرار

المحاولة الأولى أخفت سبب فشل source_connection؛ لا يمكن استنتاج السبب الجذري
من FIRST_CAPTURE_PREPARATION_FAILED. المسار المحدّث يتحقق محليًا من وجود
الإعدادات واسم المضيف المسموح وهوية pooler والمنفذ 5432 وverify-full، ثم يحمّل
CA PEM نفسها للتحقق من صيغتها، ثم يحاول DNS وTCP دون إرسال بيانات اعتماد.
ينفذ libpq بعد ذلك تحقق TLS الكامل والمصادقة والقراءات داخل معاملة read-only.
نجاح TCP وحده لا يثبت TLS أو المصادقة. لا تغيير تلقائي إلى require أو 6543
أو عنوان IP بديل، ولا إعادة تعيين كلمة مرور أو تغيير صلاحيات/RLS.

| رمز/مجموعة | دلالته والإجراء اللاحق |
| --- | --- |
| PG_CONFIG_MISSING | إعداد مطلوب فارغ؛ مراجعة أسماء الأسرار دون قيمها |
| PG_HOST_INVALID / PG_USER_INVALID / PG_PORT_INVALID | رفض الصيغة/الهوية/المنفذ قبل الشبكة؛ مطابقة Connection الرسمي لنفس المشروع |
| PG_PROJECT_UNCONFIRMED | متغير هوية المشروع لا يطابق الهدف |
| PG_SSLMODE_INVALID / PG_CA_MISSING / PG_CA_INVALID | إعداد verify-full أو ملف CA الرسمي يحتاج تصحيحًا، دون تخفيف TLS |
| PG_DNS_FAILED / PG_DNS_TEMPORARY | فشل حل الاسم، أو فشل DNS مؤقت |
| PG_NETWORK_UNREACHABLE / PG_TCP_REFUSED / PG_TCP_TIMEOUT / PG_TCP_FAILED | فشل شبكة/TCP؛ قد يلزم Session Pooler الرسمي عند غياب IPv6؛ تُجرب عناوين DNS المتاحة دون تغيير الهوية |
| PG_TLS_VERIFY_FAILED / PG_TLS_FAILED | رفض شهادة/اسم/سلسلة الثقة أو تفاوض TLS؛ لا طباعة رسالة libpq |
| PG_AUTH_PASSWORD_REJECTED / PG_AUTH_REJECTED | رفض المصادقة؛ ليس تفويضًا لإعادة تعيين كلمة المرور |
| PG_POOLER_IDENTITY_REJECTED | رد pooler يفيد رفض tenant/user؛ مراجعة اقتران المضيف واسم المستخدم بالمشروع |
| PG_PERMISSION_DENIED / PG_RLS_BYPASS_REQUIRED | نقص صلاحية أو عدم إمكان تغطية كل الصفوف؛ لا نجاح جزئي ولا تعديل صلاحيات تلقائي |
| PG_CONNECTION_LIMIT | حد الاتصالات؛ لا زيادة حدود الإنتاج تلقائيًا |
| PG_DATABASE_TOO_LARGE / PG_VERSION_UNSUPPORTED / PG_TLS_NOT_ACTIVE | بوابة السعة/PG17/TLS بعد الاتصال؛ ليست بالضرورة مشكلة كلمة مرور |
| PG_SOURCE_FAILED | فشل غير مصنف؛ لا تخمين ولا تسريب exception أو DSN |

تُقرأ SQLSTATE قبل مطابقة عبارات libpq المعروفة في الذاكرة فقط. المطابقة
تعطي فئة تشخيص ولا تكشف النص الخام. تُغلق الاتصالات التي تفشل بواباتها.
لا تحتوي السجلات قيم PGHOST/PGUSER أو كلمة المرور أو CA؛ التقرير يُظهر الرمز
الثابت ومرحلة الفشل فقط. السكربت لا يحمل مفاتيح تشفير في هذه المرحلة.

## TLS عند استخدام Session Pooler

`pg_stat_ssl WHERE pid=pg_backend_pid()` يقيس وصلة PostgreSQL إلى الطرف الذي
اتصل به؛ خلف Supavisor قد يكون هذا الطرف هو pooler وليس عميل النسخ. لذلك
لا يُستخدم هذا الاستعلام لإثبات أو نفي تشفير وصلة العميل إلى pooler.

الفحص الصحيح هنا هو `connection.pgconn.ssl_in_use` (واجهة libpq
`PQsslInUse`) للاتصال الذي أنشأه psycopg نفسه، قبل أي SQL. الاتصال يُنشأ
بـ`sslmode=verify-full` و`sslrootcert` واسم المضيف المسموح صراحةً، وليس عبر
قيمة TLS افتراضية أو خيار أضعف. تُراجع المعلمات المطبقة من `connection.info`
دون عرضها. ترفض الأداة غياب TLS أو اختلاف mode/CA/host، وتغلق الاتصال.

تختبر الاختبارات اتصالات psycopg/libpq فعلية إلى fixture محلي اصطناعي:
قبول TLS مع اسم وشهادة موثوقين، ورفض CA أخرى، ورفض اسم مضيف خاطئ، ورفض
اتصال plaintext في بوابة العميل. لا يغيّر اختبار plaintext إعدادات الإنتاج؛
يستعمل خادم اختبار محليًا فقط. تبقى معاملة المصدر read-only وفحوص الهوية
والإصدار وBYPASSRLS والسعة إلزامية.

`client_tls_verified=true` يصف وصلة عميل النسخ إلى الطرف المقصود (pooler أو
PostgreSQL المباشر). ليس شهادة منفصلة لإعداد وصلة pooler الداخلية بالخادم.
لا تغيير لإعدادات TLS في Supabase ضمن هذا الإصلاح.

## أول تشغيل فعلي — بعد الجاهزية الناجحة

Run 40318513363 أكد PG17.6 وTLS للعميل للمشروعين. الإدارة: حجم قاعدة
20,671,635 بايت، صفر buckets وصفر objects؛ البوابة: قاعدة 15,461,523 بايت،
3 buckets و31 object بإجمالي 69,349,839 بايت. هذه قياسات تلك اللحظة وليست
أرقامًا ثابتة للنسخة القادمة. فراغ الإدارة مقبول إذا تطابق SQL وGET API.

الإضافات الفعلية لكليهما: pg_stat_statements 1.11 وpgcrypto 1.3 وplpgsql 1.0
وsupabase_vault 0.3.1 وuuid-ossp 1.1. صورة restore-image.Dockerfile تبني Vault
من مصدر Supabase الرسمي عند commit 6e0cd916242d922a646e4d611cc215e09dd429f4
بعد فحص SHA-256 للأرشيف، فوق صورة PG17 مثبتة digest. لا تهيئ مخطط Supabase
افتراضيًا؛ تبدأ من cluster فارغ ليستعيد dump المخطط نفسه. يسجل Docker image
ID الناتج ويستعمل نفس الصورة المختبرة بالمعرف غير القابل للتبديل داخل job؛
لا وسم متغير ولا نشر registry أو إعداد يدوي لقيمة RESTORE_IMAGE مطلوب لهذا
المسار. حزم البناء من مستودعات Debian/PGDG الموقعة؛ البناء ليس وعدًا بتطابق
بايتات الصور بين تاريخين، لذلك يُعاد اختبار الصورة المبنية قبل كل استعمال.

حدود أول تشغيل المعتمدة في الكود المعروض للمراجعة:

| الهدف | حد قاعدة المصدر | حد Storage | حد الحزمة المشفرة اليومية |
| --- | --- | --- | --- |
| Core | 64 MiB | 16 MiB | 64 MiB |
| Portal | 64 MiB | 128 MiB | 256 MiB |

الهوامش ليست قياسًا لحجم dump النهائي. تجاوز أي حد يمنع شهادة النجاح، ولا
يقطع الملفات. سياسة السعة الحالية تفحص ميزانية 30 يومًا + نسخة قيد العمل؛
مجموع الميزانيتين 9.6875 GiB لـ31 يومًا، والحذف غير مفعّل إطلاقًا. تظل فحوص
المساحة المتاحة الفعلية إلزامية. هذه ليست موافقة على شراء مساحة مدفوعة.

backup-first-capture.yml على فرع PR فقط، لا main أو timer، وبموافقة
production-backup وcheckout مطابق SHA. قبل وصول أسرار المصدر تُبنى الصورة
وتجتاز  اختبارات التشفير والاستعادة الاصطناعية بكل الإضافات، بما فيها صف
Vault اصطناعي وملفات Storage. ثم تتحقق first_capture.py من المجلد المعلّم
الموجود المحدد للهدف، وهوية المصدر والإضافات والسعة ومفتاح التشفير، وتستدعي
المحرك الحالي للنسخ الكامل دون ترحيل أو توحيد app_state والجداول المنفصلة.

النسخة تشمل كل الجداول غير النظامية/الكائنات الكبيرة/الأدوار بلا كلمات مرور
ومخططها وصلاحياتها وتسلسلها، وجرد Storage وكل بايتاته. لا مسار انتقائي يقتصر
على reservations؛ تتضمن app_state وAuth والجداول المالية وغيرها إن سمحت
الصلاحيات، ويفشل عند العجز بدل نجاح جزئي. تُنزل الأجزاء المشفرة الأربعة
من Drive وتُفحص SHA-256 وGCM، ثم تستعاد في Docker network=none/tmpfs دون
اعتمادات إنتاج. تُقارن كل بصمات الصفوف وأعدادها والمخطط/ACL/RLS/التسلسل
والـLO وبصمات كل ملف. تطابق جميع الصفوف يشمل القيم المالية؛ لا تُطبع قيم
العملاء أو المجاميع المالية في logs.

نجاح FIRST_ENCRYPTED_CAPTURE_RESTORED يعطي backup_id ومعرف المجلد وأحجام
وبصمات الأجزاء المشفرة وأعداد الصفوف/الجداول/الملفات المتحققة. complete.json
يثبت اكتمال الرفع فقط، وrestore-ok.json دليل الاستعادة؛ لا نجاح كامل للتشغيل
إذا فشل هدف. الفشل قد يترك نسخة مشفرة غير مستعادة أو رفعًا جزئيًا في المجلد
المخصص؛ لا حذف تلقائي أو إعادة استعمال UUID أو كتابة فوق النسخ السابقة.

**حدود باقية قبل الاعتماد الكامل:** storage_service_restore_verified=false
حتى اختبار الخدمة الرسمية المعزولة عبر API؛ استعادة bytes ليست تشغيل الخدمة.
مفاتيح Vault الداخلية تديرها Supabase خارج dump: تُحفظ ciphertext كما هي،
ويُذكر عدد صفوف vault.secrets دون محتواها. وجود صفوف يتطلب خطة استرداد مفاتيح
المزوّد أو تصديرًا آمنًا معتمدًا منفصلًا؛ لا ندّعي قدرتنا على فكها من dump وحده.
vault_external_key_recovery_verified=false لا يثبت فقدًا، بل عدم اختبار هذه
التبعية. وكذلك تدوير OAuth Client Secret المكشوف لم ينفّذ، ويحتاج صلاحية مالك
Google Cloud غير المتاحة لاتصال Drive ذي drive.file. لا يبدأ cron قبل هذه
المراجعات وأدلة النسختين وموافقة المالك النهائية؛ لا تغيير مفاتيح التشفير.

لا تفعيل جدولة أو حذف أو دمج تلقائي، ولا شهادة نجاح نسخ إنتاجي حتى وجود
الحزم المشفرة للمشروعين وأدلة الاستعادة المطابقة.
