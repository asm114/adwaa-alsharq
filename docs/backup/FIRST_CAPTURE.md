## تشخيص PostgreSQL دون كشف الأسرار

المحاولة الأولى أخفت سبب فشل source_connection؛ لا يمكن استنتاج السبب الجذري
من FIRST_CAPTURE_PREPARATION_FAILED. المسار المحدّث يتحقق محليًا من وجود
الإعدادات واسم المضيف المسموح وهوية pooler والمنفذ 5432 وverify-full، ثم يحمّل
CA PEM نفسها للتحقق من صيغتها، ثم يحاول DNS وTCP دون إرسال بيانات اعتماد.
ينفذ libpq بعد ذلك تحقق TLS الكامل والمصادقة والقراءات داخل معاملة read-only.
نجاح TCP وحده لا يثبت TLS أو المصادقة. لا تغيير تلقائي إلى require أو 6543
أو عنوان IP بديل، ولا إعادة تعيين كلمة مرور أو تغيير صلاحيات/RLS.

| رمز/مجموعة | دلالته والإجراء اللاحق |
| --- | --- |
| PG_CONFIG_MISSING | إعداد مطلوب فارغ؛ مراجعة أسماء الأسرار دون قيمها |
| PG_HOST_INVALID / PG_USER_INVALID / PG_PORT_INVALID | رفض الصيغة/الهوية/المنفذ قبل الشبكة؛ مطابقة Connection الرسمي لنفس المشروع |
| PG_PROJECT_UNCONFIRMED | متغير هوية المشروع لا يطابق الهدف |
| PG_SSLMODE_INVALID / PG_CA_MISSING / PG_CA_INVALID | إعداد verify-full أو ملف CA الرسمي يحتاج تصحيحًا، دون تخفيف TLS |
| PG_DNS_FAILED / PG_DNS_TEMPORARY | فشل حل الاسم، أو فشل DNS مؤقت |
| PG_NETWORK_UNREACHABLE / PG_TCP_REFUSED / PG_TCP_TIMEOUT / PG_TCP_FAILED | فشل شبكة/TCP؛ قد يلزم Session Pooler الرسمي عند غياب IPv6؛ تُجرب عناوين DNS المتاحة دون تغيير الهوية |
| PG_TLS_VERIFY_FAILED / PG_TLS_FAILED | رفض شهادة/اسم/سلسلة الثقة أو تفاوض TLS؛ لا طباعة رسالة libpq |
| PG_AUTH_PASSWORD_REJECTED / PG_AUTH_REJECTED | رفض المصادقة؛ ليس تفويضًا لإعادة تعيين كلمة المرور |
| PG_POOLER_IDENTITY_REJECTED | رد pooler يفيد رفض tenant/user؛ مراجعة اقتران المضيف واسم المستخدم بالمشروع |
| PG_PERMISSION_DENIED / PG_RLS_BYPASS_REQUIRED | نقص صلاحية أو عدم إمكان تغطية كل الصفوف؛ لا نجاح جزئي ولا تعديل صلاحيات تلقائي |
| PG_CONNECTION_LIMIT | حد الاتصالات؛ لا زيادة حدود الإنتاج تلقائيًا |
| PG_DATABASE_TOO_LARGE / PG_VERSION_UNSUPPORTED / PG_TLS_NOT_ACTIVE | بوابة السعة/PG17/TLS بعد الاتصال؛ ليست بالضرورة مشكلة كلمة مرور |
| PG_SOURCE_FAILED | فشل غير مصنف؛ لا تخمين ولا تسريب exception أو DSN |

تُقرأ SQLSTATE قبل مطابقة عبارات libpq المعروفة في الذاكرة فقط. المطابقة
تعطي فئة تشخيص ولا تكشف النص الخام. تُغلق الاتصالات التي تفشل بواباتها.
لا تحتوي السجلات قيم PGHOST/PGUSER أو كلمة المرور أو CA؛ التقرير يُظهر الرمز
الثابت ومرحلة الفشل فقط. السكربت لا يحمل مفاتيح تشفير في هذه المرحلة.

## TLS عند استخدام Session Pooler

`pg_stat_ssl WHERE pid=pg_backend_pid()` يقيس وصلة PostgreSQL إلى الطرف الذي
اتصل به؛ خلف Supavisor قد يكون هذا الطرف هو pooler وليس عميل النسخ. لذلك
لا يُستخدم هذا الاستعلام لإثبات أو نفي تشفير وصلة العميل إلى pooler.

الفحص الصحيح هنا هو `connection.pgconn.ssl_in_use` (واجهة libpq
`PQsslInUse`) للاتصال الذي أنشأه psycopg نفسه، قبل أي SQL. الاتصال يُنشأ
بـ`sslmode=verify-full` و`sslrootcert` واسم المضيف المسموح صراحةً، وليس عبر
قيمة TLS افتراضية أو خيار أضعف. تُراجع المعلمات المطبقة من `connection.info`
دون عرضها. ترفض الأداة غياب TLS أو اختلاف mode/CA/host، وتغلق الاتصال.

تختبر الاختبارات اتصالات psycopg/libpq فعلية إلى fixture محلي اصطناعي:
قبول TLS مع اسم وشهادة موثوقين، ورفض CA أخرى، ورفض اسم مضيف خاطئ، ورفض
اتصال plaintext في بوابة العميل. لا يغيّر اختبار plaintext إعدادات الإنتاج؛
يستعمل خادم اختبار محليًا فقط. تبقى معاملة المصدر read-only وفحوص الهوية
والإصدار وBYPASSRLS والسعة إلزامية.

`client_tls_verified=true` يصف وصلة عميل النسخ إلى الطرف المقصود (pooler أو
PostgreSQL المباشر). ليس شهادة منفصلة لإعداد وصلة pooler الداخلية بالخادم.
لا تغيير لإعدادات TLS في Supabase ضمن هذا الإصلاح.

## أول تشغيل فعلي — بعد الجاهزية الناجحة

Run 40318513363 أكد PG17.6 وTLS للعميل للمشروعين. الإدارة: حجم قاعدة
20,671,635 بايت، صفر buckets وصفر objects؛ البوابة: قاعدة 15,461,523 بايت،
3 buckets و31 object بإجمالي 69,349,839 بايت. هذه قياسات تلك اللحظة وليست
أرقامًا ثابتة للنسخة القادمة. فراغ الإدارة مقبول إذا تطابق SQL وGET API.

الإضافات الفعلية لكليهما: pg_stat_statements 1.11 وpgcrypto 1.3 وplpgsql 1.0
وsupabase_vault 0.3.1 وuuid-ossp 1.1. صورة restore-image.Dockerfile تبني Vault
من مصدر Supabase الرسمي عند commit 6e0cd916242d922a646e4d611cc215e09dd429f4
بعد فحص SHA-256 للأرشيف، فوق صورة PG17 مثبتة digest. لا تهيئ مخطط Supabase
افتراضيًا؛ تبدأ من cluster فارغ ليستعيد dump المخطط نفسه. يسجل Docker image
ID الناتج ويستعمل نفس الصورة المختبرة بالمعرف غير القابل للتبديل داخل job؛
لا وسم متغير ولا نشر registry أو إعداد يدوي لقيمة RESTORE_IMAGE مطلوب لهذا
المسار. حزم البناء من مستودعات Debian/PGDG الموقعة؛ البناء ليس وعدًا بتطابق
بايتات الصور بين تاريخين، لذلك يُعاد اختبار الصورة المبنية قبل كل استعمال.

حدود أول تشغيل المعتمدة في الكود المعروض للمراجعة:

| الهدف | حد قاعدة المصدر | حد Storage | حد الحزمة المشفرة اليومية |
| --- | --- | --- | --- |
| Core | 64 MiB | 16 MiB | 64 MiB |
| Portal | 64 MiB | 128 MiB | 256 MiB |

الهوامش ليست قياسًا لحجم dump النهائي. تجاوز أي حد يمنع شهادة النجاح، ولا
يقطع الملفات. سياسة السعة الحالية تفحص ميزانية 30 يومًا + نسخة قيد العمل؛
مجموع الميزانيتين 9.6875 GiB لـ31 يومًا، والحذف غير مفعّل إطلاقًا. تظل فحوص
المساحة المتاحة الفعلية إلزامية. هذه ليست موافقة على شراء مساحة مدفوعة.

backup-first-capture.yml على فرع PR فقط، لا main أو timer، وبموافقة
production-backup وcheckout مطابق SHA. قبل وصول أسرار المصدر تُبنى الصورة
وتجتاز  اختبارات التشفير والاستعادة الاصطناعية بكل الإضافات، بما فيها صف
Vault اصطناعي وملفات Storage. ثم تتحقق first_capture.py من المجلد المعلّم
الموجود المحدد للهدف، وهوية المصدر والإضافات والسعة ومفتاح التشفير، وتستدعي
المحرك الحالي للنسخ الكامل دون ترحيل أو توحيد app_state والجداول المنفصلة.

النسخة تشمل كل الجداول غير النظامية/الكائنات الكبيرة/الأدوار بلا كلمات مرور
ومخططها وصلاحياتها وتسلسلها، وجرد Storage وكل بايتاته. لا مسار انتقائي يقتصر
على reservations؛ تتضمن app_state وAuth والجداول المالية وغيرها إن سمحت
الصلاحيات، ويفشل عند العجز بدل نجاح جزئي. تُنزل الأجزاء المشفرة الأربعة
من Drive وتُفحص SHA-256 وGCM، ثم تستعاد في Docker network=none/tmpfs دون
اعتمادات إنتاج. تُقارن كل بصمات الصفوف وأعدادها والمخطط/ACL/RLS/التسلسل
والـLO وبصمات كل ملف. تطابق جميع الصفوف يشمل القيم المالية؛ لا تُطبع قيم
العملاء أو المجاميع المالية في logs.

نجاح FIRST_ENCRYPTED_CAPTURE_RESTORED يعطي backup_id ومعرف المجلد وأحجام
وبصمات الأجزاء المشفرة وأعداد الصفوف/الجداول/الملفات المتحققة. complete.json
يثبت اكتمال الرفع فقط، وrestore-ok.json دليل الاستعادة؛ لا نجاح كامل للتشغيل
إذا فشل هدف. الفشل قد يترك نسخة مشفرة غير مستعادة أو رفعًا جزئيًا في المجلد
المخصص؛ لا حذف تلقائي أو إعادة استعمال UUID أو كتابة فوق النسخ السابقة.

**حدود باقية قبل الاعتماد الكامل:** storage_service_restore_verified=false
حتى اختبار الخدمة الرسمية المعزولة عبر API؛ استعادة bytes ليست تشغيل الخدمة.
مفاتيح Vault الداخلية تديرها Supabase خارج dump: تُحفظ ciphertext كما هي،
ويُذكر عدد صفوف vault.secrets دون محتواها. وجود صفوف يتطلب خطة استرداد مفاتيح
المزوّد أو تصديرًا آمنًا معتمدًا منفصلًا؛ لا ندّعي قدرتنا على فكها من dump وحده.
vault_external_key_recovery_verified=false لا يثبت فقدًا، بل عدم اختبار هذه
التبعية. وكذلك تدوير OAuth Client Secret المكشوف لم ينفّذ، ويحتاج صلاحية مالك
Google Cloud غير المتاحة لاتصال Drive ذي drive.file. لا يبدأ cron قبل هذه
المراجعات وأدلة النسختين وموافقة المالك النهائية؛ لا تغيير مفاتيح التشفير.

## تشخيص فشل أول تشغيل — ممنوع إعادة النسخ قبل الجرد

التشغيل 40323228407 لم يثبت نجاح أي نسخة. Core طبع جردًا مكتملًا وعدد Vault
قبل الفشل، ما يحصر المسار التالي في تحقق مفتاح التشفير؛ الرمز القديم لا يميز
المفتاح المفقود عن Base64 غير صالح أو عدد بايتات غير 32. Portal تجاوز هذا
التحقق ووصل إلى محرك النسخ ثم DriveError عام. لا دليل أن سببه مثل Core، ولا
دليل من ذلك الرمز وحده على غياب الملفات الجزئية.

`backup-failure-audit.yml` منفصل، محمي بمراجعة SHA نفسها في production-backup.
لا يمرر PGHOST أو كلمة مرور قاعدة أو مفتاح Storage، ولا يصرح بـbackup/restore.
يتحقق من صيغة المفتاح في الذاكرة دون عرض قيمته أو بصمته أو إعادة حفظه أو تغييره،
ثم يجرد أطفال المجلدين الموجودين عبر GET/list فقط. لا create/update/delete
أو تغيير أسرار/مفاتيح. الجرد الأساسي metadata فقط؛ التوسعة أدناه تسمح بقراءة
الأجزاء المشفرة المحددة للتحقق من سلامتها دون كتابة Drive. يطبع للأجزاء المعلّمة فقط معرف الملف
ومعرف النسخة والجزء والحجم وتوفر SHA-256 ورمز فحص الملكية/الخصوصية، ويعد الملفات
غير المصنفة دون عرض أسمائها أو محتوياتها. يفشل بدل قطع أكثر من 10000 ملف.

وجود complete.json أو restore-ok.json في هذا الجرد **ملاحظة فقط**؛ لا يصدر
الجرد شهادة نجاح استعادة، وتبقى `restore_verified=false` لكل مجموعة حتى فحص
الأجزاء والتشفير والاستعادة الفعلية. لا تُحذف الملفات الجزئية أو يُكتب فوقها.
يُقاس free_bytes وميزانية أول يوم/31 يومًا وتُفحص بوابات الناقل للقراءة فقط.

رموز المفتاح: ENCRYPTION_KEY_MISSING وENCRYPTION_KEY_INVALID_BASE64
وENCRYPTION_KEY_INVALID_LENGTH وENCRYPTION_KEY_VALID. لا تحويل تلقائي من hex
ولا قص/تعديل للقيمة ولا توليد مفتاح بديل. إن احتاج التصحيح مزامنة، يجب أخذ
المفتاح الأصلي المحفوظ لدى المالك، مع حفظ أي مفتاح استُخدم لنسخة موجودة.

رموز Drive التفصيلية تميز نقص السعة/عدم إمكان تأكيد quota، والمالك/خصوصية
الملف/غياب permission metadata/اشتراك غير owner-only/namespace، وتكرار الجزء،
وتعارض محتوى قائم، وعدم تأكيد الرفع أو قراءة metadata. لا يُطبع نص HTTP أو
الاستثناء. المسار الحقيقي يسجل مرحلة داخلية ثابتة مثل drive_preflight أو
drive_upload_database عند الفشل، بدل افتراض مرحلة الفشل من code عام.

نجاح READ_ONLY_FAILURE_AUDIT_COMPLETE يعني اكتمال التشخيص فقط. لا يعيد هذا
التشغيل تصدير بيانات المصدر، ويجب معالجة النتيجة وفهم الملفات القائمة قبل
اعتماد إعادة نسخ حقيقية جديدة.

أو discard sink فقط، دون SQL أو قرص أو logs. تثبت النتيجة سلامة الأجزاء فقط؛
تظل full_backup_complete=false وrestore_verified=false لغياب Storage وعلامات
الاكتمال. لا تُرفع أجزاء مفقودة ولا تُنشأ علامات في هذا الفحص ولا تُحذف القديمة.

CI كشف تعليقًا متقطعًا في نقل stdin إلى Docker CLI أثناء استعادة ملف Storage
اصطناعي. يتحقق المسار الحالي من plaintext أولًا داخل memfd مجهول في RAM،
ثم يختمه ضد التعديل ويرسله عبر Docker SDK 7.1.0 الرسمي إلى API المحلي على
unix:///var/run/docker.sock. يفحص حالة exec وانتهاءه بمهلة محدودة دون انتظار
قناة إدخال Docker CLI؛ لا ملف plaintext على قرص المضيف. تُكتب البيانات إلى
tmpfs داخل الحاوية فقط، ولا تُرفق stdout أو stderr للبيانات المنقولة.
لا fallback إلى disk أو Docker cp لكتابة plaintext. يفرّغ قارئ TAR padding
قبل انتظار انتهاء process لمنع حجب stdout. حجم الملف/البصمة/GCM تظل إلزامية،
ولا SQL قبل نجاح مصادقة كل الأجزاء. يغطي الاختبار ملفًا فارغًا وآخر غير فارغ،
ويرفض البيانات الزائدة وفشل GCM قبل إرسال أي plaintext للحاوية. Linux memfd
مطلوب؛ غيابه يفشل بأمان. RAM الإضافية بحجم أكبر جزء لا كامل النسخة؛ حدود أول
تشغيل الحالية صغيرة قياسًا بذاكرة runner والحاوية، وتبقى المهلات محدودة.

## استرداد المحاولة الجديدة 40378660548 دون تكرار التصدير

انتهت Core عند isolated_restore، بعد اكتمال رفع الأجزاء الأربعة وعلامة complete
وإعادة تنزيل الأجزاء وفحصها. Portal توقفت عند drive_upload_storage بالرمز
DRIVE_UPLOAD_UNCONFIRMED؛ لا يستنتج منه وحده وجود الملف أو غيابه أو سببه الدقيق.
لا نعيد تصدير القاعدتين أو رفع payloads لمجرد فشل الاستعادة.

اختبار جديد يحاكي دور Supabase postgres غير Superuser ودور supabase_admin
Superuser. PostgreSQL يمنع إزالة SUPERUSER من bootstrap OID 10؛ لذا تهيئة
الهدف دائمًا باسم postgres كانت غير متوافقة. المسار يختار postgres أو
supabase_admin من الأدوار الأصلية الموثقة المشفّرة بشرط Superuser وLOGIN،
ويهيئ الحاوية بذلك الاسم. يستعيد كل خصائص الأدوار الأصلية دون إسقاط ALTER
أو تخفيف المقارنة، ثم يفحصها والمخطط وكل البيانات. جميع هذه العمليات داخل
الهدف المعزول فقط؛ لا تغيير أدوار أو كلمات مرور في Supabase.

backup-recover-existing.yml مربوط بـSHA ومراجعة production-backup، ولا يحمل
PGHOST أو PGPASSWORD أو Storage API key، ويرفض السكربت وجودها. Core يستخدم
restore فقط للنسخة الجديدة التي تحمل complete. Portal يجرد المجلد الموجود
ويستبعد صراحةً المجموعة القديمة 20261026T140258Z-c8e48dde963b40949bd6023aa46f30e2.
يجب وجود مجموعة جديدة واحدة فقط بلا أجزاء مكررة وبالأجزاء الأربعة كلها.
النقص أو الالتباس يوقفه قبل كتابة أي علامة، مع إبقاء الملفات كما هي.

للمجموعة الجديدة المكتملة الأجزاء فقط: ينزل ciphertexts ويقارن SHA-256،
ويثبت GCM/AAD والمخطط والصفوف وStorage باستعادة معزولة فعلية. **بعد نجاحها
فقط** يسمح بكتابة complete.json وrestore-ok.json الناقصين، ويعيد قراءتهما.
لا رفع جديد لأي ملف .enc أو دمج أجزاء من مجموعتين، ولا استنتاج نجاح من مجرد
وجود الملفات. فشل المصادقة أو الاستعادة يمنع اعتماد المجموعة. الأصلية ذات
الأجزاء الثلاثة لا تُستكمل ولا تُعاد تسميتها ولا تُحذف.

EXISTING_CAPTURE_RESTORE_VERIFIED يعني استعادة ناجحة للمجموعة الموجودة، لا
تصديرًا حديثًا في وقت الإصلاح. يبقى زمن التقاط بيانات المصدر هو الزمن المسجل
داخل verification.enc وbackup_id. storage_service_restore_verified=false
يبقى صريحًا حتى اختبار API الرسمي المعزول، ولا تشغيل يومي أو حذف أو دمج.

## سبب رفع Portal متعدد الأجزاء — مثبت دون اتصال خارجي

النقل المخصص كان يستعمل httplib2.Http مباشرة. httplib2 0.32 يعتبر HTTP 308

Location. googleapiclient.http.build_http يزيل 308 من redirect_codes، لكن

لذلك نجحت database/roles/verification وتوقف Storage بعد أول chunk دون ملف
نهائي. test_drive_resumable_protocol.py يشغّل HttpRequest وhttplib2 الفعليين
بردود محلية مضبوطة: يعيد إنتاج RedirectMissingLocation بالنقل القديم، ويثبت
رفع كل البايتات عبر 308 ثم 200 بالنقل المصحح. لا يتضمن الاختبار Google حقيقيًا
أو OAuth. التعديل يستبعد 308 فقط، مع إبقاء TLS والتحويلات الأخرى كما هي.

محاولة استرداد 40382915222 أكدت غياب storage.enc من مجموعة Portal الجديدة؛

backup-final-retry.yml يستعيد Core الموجودة، ويعيد تصدير Portal فقط بعد
إصلاح البروتوكول. تبقى مجموعتا Portal الناقصتان دون حذف أو إعادة استخدام.

## حدود مقارنة المخطط وسياق عرض التعريفات

تصدر pg_dump مخططات التطبيق، لا information_schema القياسي. كانت بعض أجزاء
schema_query تدرج views/constraints/triggers القياسية خطأً. التحقق الحالي
يستبعد هذا المخطط النظامي وحده من تلك الأجزاء، ويعالج ملفات verification
القديمة بالطريقة نفسها. لا يستبعد public أو auth أو storage أو vault أو
أي مخطط تطبيق؛ يحتفظ باختبارات المالك وACL والأدوار وRLS وكل الصفوف.

pg_get_functiondef وpg_get_function_identity_arguments وpg_get_viewdef تعتمد
في تأهيل الأسماء على search_path. تُراجع Core بنفس اسم دور الفحص الأصلي
الممرر من سر PGUSER (دون مضيف أو كلمة مرور أو اتصال إنتاج)، وتظل استعادة DDL
وقراءة كل الصفوف بدور Superuser الأصلي داخل الحاوية. يمكن مقارنة التعريفات
ضمن سياقات عرض محددة؛ **يجب تطابق المخطط وcatalog والسياسات والأدوار
والعضويات كلها تحت سياق واحد**. لا تجاهل لاختلاف صلاحية أو تعريف تطبيق،
ولا اعتماد حقل تحت سياق وآخر تحت سياق مختلف. metadata_render_context يبيّن
السياق المتطابق برمز ثابت، وليس استعادة إعدادات منصة Supabase كاملة.

اختبار الاستعادة يضيف domain في extensions ويجري فحص المصدر تحت search_path
مختلف عن الهدف، ويثبت التطابق الكامل عند استعمال السياق المماثل. المقارنات
التي لا تتطابق تتوقف برموز RESTORE_SCHEMA_MISMATCH وRESTORE_CATALOG_MISMATCH
وغيرها؛ يُعرض اسم القسم المختلف فقط، دون SQL أو أسماء عملاء أو أسرار.

### تشخيص RESTORE_SCHEMA_MISMATCH دون تصدير جديد

التشغيل 40388793594 فشل لكلا المشروعين في مقارنة المخطط، ولم يثبت بعد
نجاح الاستعادة. الرسالة القديمة تسرد أسماء الأقسام المختلفة فقط؛ لا تكفي
لتحديد سببها أو اعتماد أنها فروق تمثيل. لا يُستثنى أي اختلاف جديد من التحقق.

المسار `backup-final-retry.yml` يستعيد الآن **المجموعات ذات complete.json فقط
للمشروعين**. لا يحمل PGHOST أو PGPASSWORD أو مفتاح Storage ولا يعيد تصدير
الإنتاج أو رفع حزم مشفرة. كل مجموعات Portal الجزئية محفوظة ولا تُستكمل
تلقائيًا. لا يكتب restore-ok إلا بعد اجتياز الفحوص الحالية كاملة.

عند الفشل، `schema_diagnostics` يبيّن لكل سياق search_path: عدد الكائنات
المتطابقة/الناقصة/المضافة، تكرار الهويات، هل الفرق ترتيب القائمة فقط، وأسماء
الخصائص المختلفة وأعدادها. عينات الاختلاف تستخدم ترتيب الكائن في وثيقة
التحقق الأصلية فقط؛ لا تنشر أسماء الكائنات أو أصحابها أو ACL أو نص SQL.
`postgres_versions` يستخرج أرقام الإصدار فقط من رأس الأرشيف والخادم المعزول.
هذه المعلومات **للتشخيص فقط**؛ المقارنة لم تتغير ولا تُقبل فروق الترتيب أو
الملكية أو التعريفات تلقائيًا.

اختبار Docker يستخدم مصدر C.UTF-8 وهدف en_US.utf8، أسماء مختلطة الحالة،
والإضافات المثبتة نفسها، ويختبر نجاح استعادة البيانات المصطنعة ورفض تغيير
مالك مخطط مع إخراج تشخيص خالٍ من القيم. لا يثبت ذلك تطابق مخطط الإنتاج؛
يلزم تشغيل محمي بعد مراجعة SHA وموافقة production-backup لتحديد السبب الفعلي.

### استكمال ملكية أعضاء الإضافات والتحقق الدلالي من ACL

التشغيل 40393446611 اكتمل بالتشخيص وفشل التحقق للمشروعين. في سياق
ROLE_DEFAULT كانت الفروق: ACL لمخططين، ACL لـ21 من 24 سجل صلاحيات افتراضية،
وملكية 49 دالة وACL لـ50 دالة. لم تختلف هويات الكائنات أو تعريفاتها في ذلك
السياق. فروق القيود والعروض والمشغلات ظهرت مع CATALOG_ONLY فقط. المصدر
PostgreSQL 17.6 وأداة dump والخادم المعزول 17.11؛ لا يجوز نسبة فروق التعريف
إلى الإصدار اعتمادًا على رسالة آخر search_path.

اختبار Docker أعاد إنتاج فشل الملكية بإنشاء الإضافات باسم postgres ثم
إسقاط SUPERUSER عنه، والاستعادة باسم supabase_admin. pg_dump يعيد إنشاء
الإضافة؛ لا يعيد تعيين ملكية كل عضو منها إلى مالكه الأصلي. يعالج
restore_metadata.py ذلك داخل حاوية الاستعادة فقط: يحدد أعضاء الإضافات من
pg_depend، ويعيد ملكيتهم ومنحهم من وثيقة التحقق الأصلية المصادق عليها بـGCM.
يشمل الدوال والعلاقات المدعومة؛ لا يستبدل تعريفات SQL ولا يصلح كائنات التطبيق
تلقائيًا. أي كائن مفقود أو سلسلة منح غير قابلة للتطبيق تفشل العملية.

تُحلل ACL الأصلية والمستعادة بواسطة aclexplode في PostgreSQL نفسه. تُقارن
كامل سجلات المانح والمستفيد والامتياز وis_grantable، مع الاحتفاظ بالتكرارات؛
يُفسر NULL بواسطة acldefault لنوع الكائن ومالكه. لا يمثل اختلاف ترتيب نص
aclitem[] اختلاف صلاحية. يظل المالك وRLS وFORCE RLS والتعريفات وسياسات RLS
والأدوار والعضويات والصفوف والتسلسل خاضعة للتحقق الكامل. يميز التحقق بين
PUBLIC (المستفيد OID=0) ودور مقتبس اسمه PUBLIC.

اختبارات الاستعادة تتضمن أذونات schema مع GRANT OPTION، وصلاحيات افتراضية
بترتيب مختلف، ومالك إضافات مختلف، ورفض تغيير مالك مخطط أو دالة تطبيق.
نجاح البيانات المصطنعة لا يثبت استعادة الإنتاج؛ يلزم اعتماد التشغيل المحمي
الذي يستعيد المجموعتين الملتزمتين الموجودتين دون تصدير جديد أو تعديل الإنتاج
أو حذف الملفات الجزئية. لا اعتماد نهائي أو جدولة قبل الأدلة الفعلية.
