# النسخ اليومي المشفر — مسودة غير مفعلة

هذا تغيير مستقل من main، لا يغير PR #164 أو الواجهة أو الحجوزات أو الحسابات أو التسلسل. لا يوجد حدث schedule في workflow، ولا موارد أو أسرار أنشئت تلقائيًا. لا تشغيل إنتاجي أو رفع فعلي أو نسخة إنتاج مكتملة في هذه الجولة.

## ماذا ينفذ

`database-backup.yml` يحوي تشغيلًا يدويًا بثلاثة أوضاع:

- `preflight`: اتصال قراءة مخول، TLS verify-full، PostgreSQL 17، هوية المشروع، وجود app_state، وفحص إعدادات التخزين الخاص؛ لا dump ولا تعديل قاعدة أو إعداد S3.
- `backup`: snapshot قراءة متسقة من PostgreSQL، بصمات الصفوف لكل الجداول العادية بكل مخططات المستخدم، dump custom كامل بلا استثناء public/auth/storage، وroles-only دون كلمات مرور، وتشفير AES-256-GCM متدفق قبل الكتابة على القرص. لا ملفات dump واضحة على runner.
- `restore`: اختيار أحدث نسخة مكتملة عمرها أقل من 48 ساعة وإعادة اختبارها؛ ليس استعادة إلى المصدر.

في وضع backup يُرفع الأرشيف المشفر وملف الأدوار والتوصيف المشفر، ومعها SHA-256 للحزم المشفرة وأحجامها. يُكتب `complete.json` أخيرًا فقط بعد انتهاء الصادرات ورفعها. **لا تعني هذه العلامة نجاح الاستعادة**. تُحذف الملفات المحلية المشفرة وتُنزل النسخة من S3، ثم تتحقق SHA-256 ومصادقة GCM قبل تنفيذ SQL. لا تُكتب `restore-ok.json` إلا بعد استعادة مستقلة ومقارنة ناجحة. marker ونتيجة الاختبار لا يحتويان أسماء العملاء أو قيم الأرصدة؛ معلومات الصفوف/ACL التفصيلية مشفرة.

التشفير يربط الحزمة بالمشروع ومعرف النسخة ونوع الملف عبر AAD؛ مفتاح خاطئ أو تغيير المحتوى أو نقل ملف من نسخة أخرى يفشل. SHA-256 للملف المشفر لا يعوض مصادقة GCM. لا تُنفذ SQL من نص مفكوك غير موثق: المرحلة الواضحة داخل tmpfs الهدف فقط، ولا يبدأ التنفيذ قبل نجاح مصادقة الحزم كلها. مفتاح التشفير يُحفظ مستقلًا عن S3 مع نسخة استرداد آمنة خارج GitHub؛ فقدانه يعني فقد إمكانية الاستعادة. لا تدوير/استبدال المفتاح قبل استعادة كل نسخ الفترة أو اعتماد خطة مفاتيح متعددة.

## متطلبات الوصول والتوافق

يوفر المالك/المشغل اتصال قراءة مخصصًا. لا تنشئ هذه الحزمة دورًا أو تمنح صلاحية إنتاجية. الدور يحتاج قراءة **جميع** مخططات المشروع وBYPASSRLS، وقدرات قراءة الأدوار والكائنات الكبيرة (large objects). لا تستعمل `--enable-row-security` أو حذف جدول لتجاوز خطأ. تطابق archive لا يُثبت اكتمالًا إذا كانت صلاحيات المصدر ناقصة، لذلك يفشل النظام عند نقص القراءة، أو foreign tables أو tablespaces مخصصة تحتاج خطة مستقلة.

اتصال مباشر أو **Session pooler على 5432** فقط، لا Transaction pooler/6543؛ المستخدم في pooler ينتهي بـ`.pgdvlklpyrvmwzitsmbw`. يتحقق TLS بـCA المشروع وverify-full، ويُثبت المشروع من المضيف/المستخدم. سر PostgreSQL لا يوضع في command line أو URI أو log؛ يمر كمتغير PGPASSWORD. جلسات snapshot وpg_dump تضبط default_transaction_read_only=on. لا execute SQL إنتاجي سوى قراءات وتصدير snapshot. هذا الإعداد لا يعوض دورًا محدود الصلاحيات؛ دوره حماية إضافية، لا ضمانًا بأن دورًا واسعًا أصبح غير قادر على الكتابة.

التوصيف داخل نفس snapshot الذي يستعمله pg_dump؛ يشمل app_state وJSON المالي وكل الصفوف، وACL وRLS وملكية الكائنات والأدوار والعضويات والكائنات الكبيرة. تسلسلات PostgreSQL ليست MVCC؛ إذا تغيرت أثناء التصدير يفشل التشغيل بدل الادعاء باتساقها. يلزم اختبار نافذة حمل مناسبة. مصدر الأدوار يُفحص مجددًا بجلسة قراءة مستقلة، ويقارن بعد الاستعادة أيضًا. لا يُستدعى nextval أو تصحيح قيود/أرصدة على المصدر.

عملاء pg_dump/pg_dumpall يعملون من صورة PostgreSQL17 ثابتة بـdigest؛ لا نعتمد على نسخة apt في runner. شهادة CA تُركب read-only، وتُمرر متغيرات PostgreSQL فقط إلى حاوية العميل دون مفاتيح S3 أو التشفير. حاوية المصدر تحتاج شبكة للقراءة، بينما هدف الاستعادة منفصل network=none. PG17 مطلوب؛ صورة الهدف مثبتة بـdigest ويجب أن تدعم امتدادات المصدر وملكيته وأدواره. الإنتاج يحوي `supabase_vault` و`pgcrypto` و`uuid-ossp` و`pg_stat_statements` و`plpgsql` حسب قراءة الكتالوج في 2026-10-24. صورة postgres العادية تستعمل لاختبارات البيانات المصطنعة فقط، وليست ضمانًا لاستعادة Supabase. الأدوار المحجوزة/خصائص postgres وVault/مفاتيحه وإعدادات المنصة قد تتطلب هدف Supabase متوافقًا وخطة مخولة؛ أي فشل يُبقي gate مفتوحًا، ولا تُحذف هذه الكائنات لتجميل النتيجة. استثناء CREATE ROLE postgres الوحيد في الاختبار سببه أن initdb أنشأه؛ تبقى خصائصه ومنحه كما في المصدر، وقد ترفضها وجهة غير متوافقة.

## التخزين والتكلفة قبل التفعيل

التنفيذ المستهدف AWS S3 خاص موجود ومعتمد، لا Google Drive ولا bucket عام. لا ننشئ bucket أو حسابًا أو خدمة مدفوعة. يلزم:

1. إقرار المنطقة والمالك وسياسة الوصول والتكلفة. تقدير شهري: 30 × متوسط حجم النسخة المشفرة + الإصدارات القديمة القصيرة + طلبات S3 وقراءة الاستعادة ونقل البيانات ودقائق Actions. لا رقم تكلفة نهائي دون حجم وregion وخطة الحساب. المستودع عام؛ لا يفترض أن كل دقائق runners/نقل/S3 مجانية.
2. Block Public Access بالكامل، سياسة bucket غير عامة (مع منع HTTP غير المشفر)، BucketOwnerEnforced، versioning وserver-side encryption. إن استُعمل SSE-KMS تلزم صلاحيات KMS وتسعيرها ومفتاح استرداد أيضًا. التشفير المحلي لا يُعطل.
3. تطبيق lifecycle الموجود في `lifecycle-example.json` بعد اعتماد المالك على **هذا prefix فقط**. يحتفظ الإصدار الحالي 30 يومًا، وينظف الإصدارات غير الحالية بعد يوم واحد؛ دورة S3 غير فورية وقد تتجاوز 30 يومًا بوقت المعالجة وتنظيف الإصدارات. لا نستعمل noncurrent=30 لأن ذلك قد يضاعف فترة بقاء نسخة حُذفت عند اليوم 30. Object Lock المفعّل يوقف preflight حتى اعتماد خطة احتفاظ وتكلفة منفصلة؛ أي سياسات أخرى قد تمنع الحذف تُراجع أيضًا.
4. هوية AWS مقيدة بـprefix. `iam-example.json` قالب يراجعه المشغل، وليس سياسة مطبقة. لا List/Get على بيانات أخرى، ولا DeleteObject أو إنشاء موارد أو تغيير policies. التنظيف من lifecycle وحده. OIDC قصير العمر أفضل مستقبلًا؛ هذه المسودة تدعم GitHub Secrets مقيدة ومدوّرة، مع session token اختياري. لا سر AWS في image أو dump أو subprocess التصدير.

يمتنع التنفيذ إذا فشلت إعدادات الخصوصية أو الاحتفاظ أو الموافقات. `preflight` يفحص السياسات فقط؛ نجاح Put/Get الحقيقي والحصص والشبكة يُثبت بتجربة النسخة والاستعادة، لا من فحص HEAD وحده. عند فقد رد رفع أو فشل multipart لا تُنشأ علامة complete؛ قد تبقى أجزاء مشفرة ينظفها lifecycle. لكل تشغيل اسم UUID جديد؛ لا حذف أو استبدال نسخة سابقة.

## إعداد GitHub مرة واحدة بواسطة مشغل مخول

المكان: المستودع → Settings → Environments → **production-backup**. يجب إنشاء البيئة أولًا مع reviewers معتمدين وقيود deployment على main ومنع self-review حيث تسمح الخطة. لا تترك GitHub ينشئ بيئة بلا حماية تلقائيًا. workflow يقبل main فقط، ولا يسحب أسرارًا عبر pull_request أو pull_request_target. بيئة التنفيذ الحالية بلا الاعتمادات؛ فحص أسماء GitHub Secrets رُفض بـ403، لذلك لا نفترض أنها غير موجودة أو جاهزة. البيئة المطلوبة لم تكن ضمن قائمة البيئات عند المراجعة.

أسرار البيئة:

| الاسم | القيمة التي يضعها المشغل في واجهة Secrets فقط |
|---|---|
| BACKUP_PGHOST | مضيف direct/session pooler للمشروع |
| BACKUP_PGUSER | مستخدم القراءة المخول، مع project suffix عند استعمال pooler |
| BACKUP_PGPASSWORD | كلمة مرور دور النسخ، لا كلمة مرور حساب Supabase |
| BACKUP_CA_PEM | شهادة CA الرسمية للمشروع، لا تعطيل التحقق |
| BACKUP_ENCRYPTION_KEY | مفتاح عشوائي 32 بايت مشفر Base64، مع نسخة استرداد مستقلة |
| BACKUP_AWS_ACCESS_KEY_ID / BACKUP_AWS_SECRET_ACCESS_KEY | هوية S3 المقيدة والمعتمدة |
| BACKUP_AWS_SESSION_TOKEN | عند استعمال جلسة مؤقتة؛ غير مطلوب للمفتاح الثابت |

متغيرات البيئة غير السرية: BACKUP_AWS_REGION، BACKUP_BUCKET، BACKUP_BUCKET_OWNER (رقم الحساب 12 خانة)، BACKUP_RESTORE_IMAGE (صورة متوافقة مع digest). BACKUP_COST_APPROVED وBACKUP_EXECUTION_APPROVED وBACKUP_RESTORE_APPROVED يجب أن تكون `true` **فقط بعد اعتماد كل منها**. لا تضعها true لتجاوز إخفاق. لا تنشئ الحزمة هذه الإعدادات أو الأسرار أو تغييرات DB بنفسها.

فحص المصدر يرفض حجم قاعدة يتجاوز BACKUP_MAX_DATABASE_BYTES (افتراضيًا 1GiB) قبل التصدير. التحميل من S3 يرفض حزمة مشفرة تتجاوز 2GiB أو حجمًا مخالفًا للـmanifest. لا تعني هذه الحدود أن السعة تكفي لكل امتداد أو workload؛ الاستعادة الفعلية هي الحكم.

السعة الحالية للهدف: ذاكرة 4GiB وtmpfs للقاعدة 4GiB ولأرشيف الاستعادة 4GiB، CPU=2 وpids=256، دون ports أو شبكة أو credentials إنتاجية داخله. لا تُرفع سعتها أو يُختَر runner مدفوع دون مراجعة حجم المصدر وتكلفته. توقيت workflow أقصاه 90 دقيقة. إذا تجاوز المصدر السعة يفشل الاختبار ويحتاج هدفًا مخولًا مناسبًا، لا استعادة في الإنتاج.

## بوابات أول تجربة وتفعيل اليومي

1. مراجعة PR وخطة التخزين/التكلفة وقدرات القراءة والهدف المتوافق. لا دمج أو نشر أو تفعيل جدول ضمن هذه المهمة.
2. أول تجربة إنتاج تحتاج أسرارًا معتمدة داخل بيئة سحابية محمية وتشغّل **نفس السكربت**؛ لا جهاز المالك. مثال بعد إعداد الاعتمادات وRUNNER_TEMP خارج المستودع: `GITHUB_REF=refs/heads/ops/encrypted-daily-backup-20261024 python tools/backup/backup.py preflight` ثم backup عند اعتماد العملية والهدف. لا تضع القيم الحساسة في أمر shell. هذه البيئة الحالية لا تحتويها، لذلك لم ننفذ التجربة. لا تنقل أسرار GitHub إلى logs لإتاحتها للمساعد.
3. بعد موافقة دمج منفصلة مستقبلًا، يصبح workflow_dispatch متاحًا من main. GitHub قد لا يعرض workflow جديدًا أو يقبل dispatch قبل وجوده على default branch؛ لا نعتبر غيابه نجاحًا أو ندمج لتجاوز بوابة الاختبار. يمكن التحقق الأول من البيئة السحابية المعتمدة المذكورة أعلاه.
4. لابد من نجاح رفع **حقيقي** ثم قراءة النسخة من S3 وفك تشفيرها واستعادتها ومقارنة كل الصفوف والتسلسل والمالية وACL. سجل SHA للسكربت ومعرف النسخة ونتيجة restore-ok والرابط وهوية الهدف دون معلومات حساسة. لا يثبت الاختبار المصطنع هذه الخطوة.
5. اعتماد المالك الصريح للتفعيل بعدها فقط، مع إصدار تغيير منفصل يضيف حدث cron يوميًا (مقترح 00:00 UTC = 03:00 الرياض) إلى workflow ويختار operation=backup لحدث cron. لا يوجد هذا الحدث حاليًا، ولا مسار افتراضي للتشغيل المجدول. كل نسخة يومية مصممة لاختبار استعادتها أيضًا؛ يحقق ذلك اختبارًا دوريًا يوميًا لكنه يزيد الدقائق ويحتاج إقرار التكلفة، ويمكن لاحقًا فصل الاستعادة أسبوعيًا بقرار معتمد.
6. اختبار التنبيه بإخفاق مصطنع مضبوط بعد الاعتماد، والتحقق من وصوله للمشغل. job الفشل يفتح/يحدث Issue واحدة بوصلة run دون تفاصيل DB، مع تعيين المسؤول من متغير المستودع BACKUP_ALERT_ASSIGNEE (افتراضيًا مالك المستودع إن كان حساب مستخدم)، وإشعار Actions الأصلي. المستودع يدعم Issues، لكن لم يُرسل تنبيه فعلي الآن لأن تشغيل الإنتاج غير معتمد. يجب أن يراقب المسؤول Issue/Actions وتُختبر صلاحية token وسياسة المنظمة؛ تعطل GitHub نفسه يحتاج مراقبة مستقلة عند اعتمادها.

تعطيل التشغيل: إزالة موافقة BACKUP_EXECUTION_APPROVED أو تعطيل workflow. لا يعيد ذلك نسخة قديمة فوق الإنتاج ولا يحذف ملفات S3. تحتفظ هذه الحزمة بحق النسخ/القراءة فقط؛ أي استرداد بيانات إلى الإنتاج حادث مستقل يحتاج موافقة صريحة.

## Supabase Storage والخدمات

فحص قراءة metadata بتاريخ 2026-10-24: **0 buckets و0 objects و0 reported bytes**؛ لم تُقرأ ملفات أو أسماء عملاء. هذا ليس ضمانًا بأن Storage سيظل فارغًا. dump يتضمن metadata الموجودة في قاعدة البيانات، وليس ملفات Storage نفسها. كل manifest اختبار استعادة يعلن storage_files_verified=false ولا يدعي نسخها.

قبل التفعيل يُعاد فحص inventory؛ عند إضافة buckets/ملفات تحتاج مهمة مستقلة معتمدة: قائمة جميع المفاتيح/الإصدارات، تنزيل عبر API/S3 مخول بالقراءة، تشفير المحتوى وفهرس الأسماء، SHA-256 وحجم لكل ملف، احتفاظ 30 يومًا، واستعادة إلى bucket اختبار خاص مع مقارنة bytes وRLS/الوصول. لا service_role في الواجهة؛ لا إعادة رفع أو حذف إلى production. لا تنفذ هذه المسودة نسخ Storage تلقائيًا لعدم وجود ملفات ولعدم توفر اعتمادات/موافقة تكلفتها. Auth provider settings وSMTP وEdge Functions ومفاتيح Vault وRealtime/webhooks/cron تحتاج جردًا منفصلًا؛ يعزل الهدف الشبكة حتى لا ينفذ إرسالًا خارجيًا أثناء الاستعادة.

## الاختبارات وحدود التسليم

`backup-isolated-tests.yml` يعمل على PR بأسرار **مصطنعة فقط**. يغطي التشفير والتلاعب والمفتاح الخاطئ وAAD والاحتفاظ والخصوصية وبوابات الموافقة/TLS، ثم dump فعلي في PostgreSQL17 لستة جداول مصطنعة (app_state، حجوزات قديمة/جديدة، دفعات، مصاريف، صيانة بالتقسيط، عمولات) وعلاقاتها وRLS وتسلسل الهوية وكائن كبير. يستعيد في خادم آخر network=none ويقارن البصمات والصفوف والملكية والصلاحيات والتسلسل دون تغيير المصدر. هذه اختبارات منتج النسخ فقط، لا تغيير للحسابات أو اختبارات كتابة إنتاجية.

الحالة: تنفيذ المسودة قابل للاختبار، **النسخ اليومي غير مفعل وغير معتمد إنتاجيًا**. لا نسخة إنتاجية أو تخزين مدفوع أُنشئ. يلزم اعتماد التخزين/التكلفة والاعتمادات والهدف المتوافق ونجاح أول تجربة حقيقية ثم موافقة التفعيل. PR #164 يبقى منفصلًا دون تغيير.

مراجع: [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)، [Supabase backup reader](https://supabase.com/docs/guides/troubleshooting/pg_dump-fails-with-query-would-be-affected-by-row-level-security-policy-1d5783)، [Supabase backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)، [S3 lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html).
