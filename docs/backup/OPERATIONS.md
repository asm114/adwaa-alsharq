# تشغيل واستعادة نسخ Drive — بوابة تفعيل مغلقة

هذا الدليل يكمل PR #165 ولا ينشئ محركًا آخر. رفع ADWAA-CONNECTION-TEST.txt يثبت المسار الذي استُخدم للتجربة فقط؛ لا يثبت أن الأسرار وصلت للمشغل أو أن dump قاعدة الإنتاج قابل للاستعادة. لا توجد جدولة مفعلة أو تصريح حذف.

## ما يغطيه المحرك وما لا يغطيه

- المصدر مقيد بالمشروع pgdvlklpyrvmwzitsmbw وبـPG17 وباتصال TLS verify-full على direct أو Session Pooler في 5432. إصدار آخر يفشل بدل استعمال عميل غير متوافق.
- pg_dump كامل، بلا قائمة أسماء جداول وبلا حصر public: يشمل app_state/main وJSONB بكل مفاتيحه، وأي جداول حجوزات وعملاء ودفعات ومصروفات وصيانة واشتراكات وتقسيط وعمولات موجودة في هذه القاعدة، والجداول الفارغة والمخططات غير العامة. دور ناقص الصلاحيات/RLS لا يُقبل كنسخ كامل. الجداول الأجنبية/tablespaces غير الافتراضية تحتاج خطة مستقلة ويفشل المحرك عند وجودها.
- مقارنة عدد وبصمة كل صف بعد الاستعادة تحمي القيم المالية كما هي دون إعادة حساب أو توحيد مصادر. الاختلاف بين app_state والجداول المنفصلة محفوظ كما هو؛ لا ترحيل ولا تقرير أن أحد المصدرين صحيح تلقائيًا.
- يشمل المخطط والملكية وRLS وACL والأدوار والعضويات والتسلسل والكائنات الكبيرة. كلمات مرور أدوار PostgreSQL مستبعدة عمدًا؛ يلزم إجراء مستقل لإعادة ربط الحسابات عند استرداد كارثة.
- لا يشمل محتوى ملفات Supabase Storage، ولا قاعدة مشروع بوابة العملاء المنفصل، ولا ملفات المستخدم المحلية أو كل إعدادات منصة Supabase ووظائفها المنشورة. بيانات storage.objects داخل dump ليست الملفات نفسها. لا تسمِّ هذه النسخة وحدها «حماية لجميع أصول أضواء الشرق». يلزم جرد مستقل لهذه الأصول وخطة نسخ واستعادة قبل ذلك الوصف.
- صور الاستعادة يجب أن تحتوي امتدادات المصدر بنفس الإصدارات وبصورة متوافقة ومثبتة digest. فشل امتداد Supabase أو مقارنة كتالوج لا يُعالج بإسقاطه أو تجاهل الخطأ.

## الأسرار — إدخال آمن

GitHub → Settings → Environments → production-backup. اضبط الحماية وreviewers ومنع self-review وقيود main حيث تتيح الخطة ذلك. لا تضع القيم في ملفات المستودع أو Issue أو محادثة أو أمر shell أو لقطة شاشة. استخدم محرر Secrets الآمن مباشرة؛ لا تعِد استخراج رمز المستخدم المحلي أو طباعته. لا تستخدم أسرار إنتاج في اختبارات PR.

| Environment Secret | المحتوى المطلوب |
|---|---|
| BACKUP_DRIVE_CLIENT_ID | معرف عميل OAuth الذي أصدر الرمز |
| BACKUP_DRIVE_CLIENT_SECRET | سر العميل نفسه |
| BACKUP_DRIVE_REFRESH_TOKEN | رمز المالك، offline وبنطاق drive.file فقط |
| BACKUP_ENCRYPTION_KEY | 32 بايت عشوائية بصيغة Base64؛ احتفظ بنسخة استرداد مشفرة منفصلة عن Drive وGitHub |
| BACKUP_PGHOST | مضيف direct أو Session Pooler للمشروع المحدد، دون مخطط أو مسار |
| BACKUP_PGUSER | المستخدم المخول للقراءة؛ اسم pooler مرتبط بمرجع المشروع |
| BACKUP_PGPASSWORD | كلمة المرور للحساب نفسه؛ لا رابط اتصال كامل |
| BACKUP_CA_PEM | سلسلة CA الرسمية الموثوقة اللازمة لـverify-full |

لا تضع Access Token مؤقتًا مكان Refresh Token. External OAuth بوضع Testing ليس اعتمادًا دائمًا: قد تنتهي الرموز بعد 7 أيام. المحرك يرفض scope واسعًا أو غير مؤكد في رد التجديد؛ إذا رفض رمزًا نجح في أداة أخرى فافحص grant وإعداد العميل، ولا تعطل فحص scope لتجاوز الخطأ. لا تنسخ رمز المتصفح القديم.

Environment Variables: BACKUP_DRIVE_ACCOUNT، BACKUP_DRIVE_FOLDER_ID، BACKUP_DRIVE_ESTIMATED_DAILY_BYTES (حجم الحزمة الكاملة لا ملف واحد)، BACKUP_MAX_DATABASE_BYTES، BACKUP_RESTORE_IMAGE (digest معتمد)، BACKUP_ALERT_ASSIGNEE. البريد ومعرف المجلد معلومات تشغيلية؛ لا تنشرها بلا داعٍ. بوابات BACKUP_EXECUTION_APPROVED وBACKUP_COST_APPROVED وBACKUP_RESTORE_APPROVED وBACKUP_DRIVE_SETUP_APPROVED تبقى غير معتمدة حتى مراجعة العملية التي تتيحها.

## ترتيب التحقق اليدوي

الـworkflow معرّف يدويًا فقط ومقيد بـmain؛ لا تدمج PR لتجاوز هذا القيد. قبل الدمج يمكن تشغيل السكربت نفسه في بيئة محمية معتمدة ذات اتصال PG وDocker وصورة الاستعادة المناسبة، مع حقن المتغيرات بأداة الأسرار. لا توجد أسرار مخزنة في تعليمات التشغيل.

بعد اعتماد كل خطوة:
1. init-drive: إنشاء/إعادة استخدام المجلد الجديد المعلّم الخاص بالمحرك فقط، لا مجلد JSON القديم. يحتاج اعتماد إنشاء المجلد؛ لا تستعمل مجلد اختبار الاتصال عشوائيًا.
2. preflight: فحص Google والحساب والملكية والخصوصية والمساحة ثم اتصال PG/TLS والمشروع؛ لا dump.
3. backup: لقطة قراءة واحدة، dump وتشفير ورفع؛ ثم تنزيل فعلي من Drive وفحص SHA-256 وGCM واستعادة معزولة ومقارنة. لا نجاح حتى restore-ok.json. complete.json وحده لا يثبت الاستعادة.
4. health: فحص metadata فقط؛ يفشل عند غياب النسخة أو عمر 48 ساعة/تاريخ مستقبلي، أو غياب restore-ok المطابق لأحدث complete، أو نقص جزء/اختلاف حجمه. لا يفك تشفيرًا أو يتصل بقاعدة أو يكتب ملفات Drive. ليس بديلًا عن إعادة اختبار الاستعادة، ولا يثبت تغطية Storage.

لا تعِد تشغيل init-drive أو backup تلقائيًا إذا كانت نتيجة الكتابة السابقة غير معروفة قبل مراجعتها؛ لا تحذف النسخ القديمة لحل نقص المساحة.

## طريقة اختبار الاستعادة

باستخدام أسرار البيئة المحمية ونفس نسخة السكربت المعتمدة والتبعيات المثبتة، شغّل:

```sh
python tools/backup/backup.py restore
```

لا تستخدم رابط الإنتاج كهدف استعادة. الوضع restore ينزل أحدث complete حديثة فقط، يفحص الحجم وSHA-256 وهوية النسخة ومصادقة AES-GCM، ثم يستعيد إلى Docker جديد network=none بلا منافذ أو أسرار المصدر؛ البيانات الواضحة في tmpfs. تُقارن كل الصفوف والمخطط والكتالوج والأدوار والتسلسل والكائنات الكبيرة قبل marker النجاح، ثم تحذف الحاوية. البيانات الاصطناعية وحدها في اختبارات CI. استعادة نسخة قديمة/كارثة فعلية أو استبدال قاعدة تطبيق تحتاج إجراء منفصلًا معتمدًا؛ لا تعدل نافذة 48 ساعة أو ضوابط الهدف بصورة عشوائية.

## الفشل ومراقبة غياب التشغيل

الـworkflow يبلغ عبر Issue عامة برسالة ثابتة ورابط التشغيل فقط دون أخطاء قاعدة أو أسرار عند الفشل أو الإلغاء؛ اجعل BACKUP_ALERT_ASSIGNEE حسابًا صالحًا وفعل إشعاراته وتحقق من صلاحية issues:write. فشل الإشعار نفسه ظاهر كفشل job، وليس نجاح النسخ.

غياب تشغيل workflow كليًا لا يمكن اكتشافه من ذلك التشغيل نفسه. بعد تفعيل مستقبلي معتمد، يلزم فحص health دوري مستقل/مراجعة خارجية لإشعار غياب تشغيل أو نسخة حديثة. مثال يدوي الآن: workflow_dispatch operation=health بعد إتاحة workflow على main وباعتماد البيئة. لا توجد مراقبة دورية فعالة حاليًا، ولا وعد بضمان وقت GitHub cron.

## إعداد الجدولة دون تفعيل الآن

الخطة في activation-plan.json: 00:00 UTC = 03:00 الرياض يوميًا، احتفاظ مقترح 30 يومًا. لا schedule trigger في workflow، وبوابات BACKUP_SCHEDULE_APPROVED وBACKUP_PRODUCTION_RESTORE_VERIFIED وBACKUP_DRIVE_RETENTION_APPROVED ثابتة false.

لا تُغيَّر هذه القيم أو enabled ولا يُضاف cron حتى: نسخة إنتاجية فعلية مستعادة بنجاح مع دليل، اكتمال نطاق الأصول/القيود، اختبار إنذار وhealth، كفاية سعة Drive والـrunner، ثم موافقة المالك الصريحة ومراجعة تعديل مستقل. الحذف يحتاج اعتمادًا منفصلًا؛ لا تجعل نجاح الجدولة موافقة ضمنية على الحذف.
