# نسخ PostgreSQL إلى Google Drive — مسودة غير مفعلة

هذا PR #165 مستقل عن PR #164. لم تُغير الواجهة أو JSON backups أو الحجوزات أو المالية أو التسلسل. Drive هو الوجهة الافتراضية بدل AWS في workflow. أُعيد استعمال محرك pg_dump وAES-256-GCM والتحقق والاستعادة الموجود؛ أُضيف transport adapter فقط. دعم S3 محفوظ كخيار صريح في السكربت (`BACKUP_STORAGE_PROVIDER=s3`)، دون fallback تلقائي عند خطأ Drive؛ [مرجعه السابق](S3-optional.md) وقوالب IAM/lifecycle لم تُطبق.

## ما وُجد سابقًا — مراجعة قراءة فقط في 2026-10-25

- الحساب المتصل بأداة Drive يطابق الحساب الذي حدده المالك. ظهر مجلد **Adwaa Al Sharq Backups**، أنشئ في 2026-07-23، وmetadata تعرض shared=false. لم يُسجل البريد أو معرف المجلد القديم في هذا التقرير العام أو في الأسرار أو السكربتات.
- بحث الأبناء داخل ذلك المجلد، وبحث أسماء Adwaa-backup، لم يُظهر ملفات متاحة للأداة. **لا نجزم بأن كل النسخ مفقودة أو المجلد خالٍ فعليًا**: هذا ما أعادته أداة البحث المتصلة فقط، وليس جردًا غير مقيد لكل ملفات الحساب أو أجهزته أو سلة المهملات. لم يُنزل محتوى أي نسخة أو يُعدل أي ملف/مجلد.
- في index.html تكامل Google Identity Services بنطاق drive.file واسم المجلد أعلاه. الرمز access token في ذاكرة الصفحة وينتهي، ولا refresh token خادمي موجود بهذا المسار. إنشاء النسخة يفحص JSON التطبيق ويحفظه في IndexedDB أو مجلد الجهاز المختار/تنزيله، ثم يحاول رفعه إلى Drive وتسجيله في Supabase.
- توجد نسخ تلقائية **مرتبطة بإجراء** مثل التغيير أو الاستعادة/الترحيل، ونسخ يدوية. لم نجد في المستودع الحالي scheduler قديمًا لنسخ PostgreSQL يوميًا يعمل عند إغلاق الجهاز؛ اسم daily-stability-checks يعني اختبارات وليس نسخ قاعدة. لا يكفي هذا لنفي أتمتة خارج المستودع لا نملك رؤيتها.
- النسخ السابقة JSON للتطبيق، وليست roles/schema/data لكامل PostgreSQL ولا نسخ ملفات Storage. يمكن إبقاؤها والاستفادة منها في خدمة التطبيق الموجودة؛ لا تُحوّل تلقائيًا إلى backup قاعدة ولا تستبدل أو تحذف. المخازن المحلية على أجهزة المالك غير قابلة للفحص من هذه البيئة. لم يُعد فتح إصلاحات PR #164.

**قرار إعادة الاستخدام:** إعادة استخدام حساب Drive ومساحته مناسبة مشروطًا بسعة فعلية وتفويض offline. لا يمكن نقل رمز جلسة المتصفح أو اتصال ChatGPT إلى GitHub Secrets، ولا إعادة استعماله كاعتماد يومي. نستخدم عميل OAuth مستقلًا ومجلدًا جديدًا خاصًا لنسخ PostgreSQL، ليظل المجلد والنسخ القديمة خارج نطاق أي احتفاظ مستقبلي.

## المحرك القائم وما يثبته

pg_dump من عميل PG17 ثابت بـdigest، custom archive كامل بلا حصر public، في snapshot قراءة REPEATABLE READ مشتركة مع بصمات الجداول (ومنها app_state وJSON المالية). roles-only بلا كلمات مرور؛ مقارنة الأدوار والعضويات وملكية الكائنات وRLS وACL والمخطط والدوال/العروض/القيود والامتدادات والكائنات الكبيرة والتسلسل. لا تعديل أو nextval أو ترحيل على المصدر.

AES-256-GCM متدفق قبل القرص، AAD يربط الملف بالمشروع ومعرف النسخة. الحزم المشفرة وحدها في RUNNER_TEMP خارج المستودع، SHA-256 وحجم لكل حزمة. ملفات البيانات لا تدخل GitHub artifacts أو logs. ملف verification التفصيلي مشفر أيضًا. مفتاح 32 بايت Base64 عالي العشوائية في Secret منفصل مع نسخة استرداد خارج GitHub/Drive؛ لا تدويره قبل اعتماد طريقة فك تشفير النسخ القديمة.

Drive يرفع ملفات binary مشفرة إلى المجلد الجديد فقط، بأسماء ومعرفات ثابتة لكل object. يحجز file ID قبل الرفع، ثم يتحقق من owner/parent/namespace وSHA-256 والحجم عبر Drive. ضياع الرد يتحقق من ID نفسه ولا ينشئ ID آخر عند نتيجة مجهولة. ملف موجود بمحتوى مختلف لا يستبدل. الأخطاء والمهل/الحصة لا تُعرض نجاحًا، ولا توجد محاولة S3 بديلة صامتة.

complete.json يكتب بعد رفع الأجزاء فقط؛ لا يعني نجاح الاستعادة. تُحذف الحزم المحلية المشفرة وتُنزل **النسخة من Drive**، وتُفحص البصمة ومصادقة GCM قبل تنفيذ SQL. استعادة في Docker مستقل network=none، دون منافذ أو credentials المصدر أو مجلدات host، وtmpfs فقط للبيانات الواضحة. restore-ok.json لا يكتب قبل تطابق الفحوص. عدم توافق امتدادات Supabase/الأدوار أو نقص البيانات يبقي البوابة مفتوحة، ولا تُحذف كائنات لتجميل النتيجة.

## Google OAuth محدود الصلاحيات

تفويض مستقل لمرة واحدة للحساب المحدد، باستخدام OAuth Authorization Code مع state وPKCE وaccess_type=offline في جلسة موثوقة، والنطاق الوحيد:

`https://www.googleapis.com/auth/drive.file`

لا كلمة مرور Google ولا service account JSON أو access token من أدوات المساعد. لا نطاق drive الكامل أو domains delegations. العميل الجديد لا يعدل إعداد عميل المتصفح القديم. drive.file يرى الملفات التي أنشأها التطبيق/اختارها المستخدم له، وليس كل تاريخ Drive؛ لذلك لا نفترض رؤية ملفات التطبيق القديم. تفعيل Drive API في مشروع Google Cloud وربط حساب المالك بالتطبيق وإتمام شاشة الموافقة مطلوبان؛ اتصال المساعد الحالي لا يوفر refresh token للمشغل ولا تُستخرج رموزه.

refresh token وclient secret في GitHub Environment Secrets فقط؛ يجدد google-auth رموز الوصول في الذاكرة عبر endpoint ثابت، ولا تُطبع الرموز أو تتخزن في الكود. يُرفض granted_scopes الكامل أو غير المؤكد بدل قبول صلاحية أوسع. يجب أن يصدر refresh token أصلًا لتطبيق مستقل بنطاق drive.file فقط، لا إعادة استخدام grant واسع. إذا تغيرت الصلاحية أو أُلغي التفويض يفشل التشغيل ويرسل التنبيه القائم، دون طلب كلمة مرور.

**قيد مهم:** تطبيق External في وضع Testing قد تنتهي refresh tokens الخاصة به بعد 7 أيام لهذه الصلاحية؛ لا يصلح تشغيلًا دائمًا على هذا الأساس. يلزم إعداد نشر OAuth مناسب للحساب والحفاظ على التفويض. drive.file نطاق موصى به غير حساس، لكن Google قد يطلب متطلبات نشر/هوية/سياسات بحسب التطبيق. لا وعد بأن التفويض لن يُلغى أو بأن حسابًا شخصيًا يدعم service account لتملك ملفات؛ حساب الخدمة ليس بديلًا مباشرًا عن OAuth مالك My Drive.

## الربط الآمن وإعداد GitHub

المكان: Repository Settings → Environments → **production-backup** مع reviewers ومنع self-review وقيود main حيث تسمح الخطة. لا تترك البيئة تُنشأ دون حماية. Workflow موجود في PR فقط وقد لا يقبل workflow_dispatch قبل وجوده على default branch؛ لا ندمج لتجاوز ذلك. أول تجربة يمكن تشغيل **السكربت نفسه** من بيئة سحابية محمية ومعتمدة بعد توفير الأسرار، دون كمبيوتر المالك. لا إعداد لهذه البيئة أو أسرار أو شراء موارد نُفذ هنا.

أسرار البيئة:

| Secret | الغرض |
|---|---|
| BACKUP_DRIVE_CLIENT_ID | عميل OAuth الجديد |
| BACKUP_DRIVE_CLIENT_SECRET | سر العميل، لا كلمة مرور Google |
| BACKUP_DRIVE_REFRESH_TOKEN | grant offline محدود للحساب المحدد |
| BACKUP_ENCRYPTION_KEY | مفتاح 32 بايت عشوائي Base64 مع نسخة استرداد مستقلة |
| BACKUP_PGHOST / BACKUP_PGUSER / BACKUP_PGPASSWORD | اتصال قراءة مخول للمشروع |
| BACKUP_CA_PEM | CA الرسمية لاتصال verify-full |

متغيرات البيئة: BACKUP_DRIVE_ACCOUNT (البريد المتوقع)، BACKUP_DRIVE_FOLDER_ID (المجلد الجديد)، BACKUP_DRIVE_ESTIMATED_DAILY_BYTES (ميزانية حجم **الحزمة المشفرة كاملة** مع markers)، BACKUP_RESTORE_IMAGE (هدف PG17 متوافق ومثبت digest)، BACKUP_MAX_DATABASE_BYTES (افتراضي 1GiB). التنفيذ يتطلب BACKUP_EXECUTION_APPROVED وBACKUP_COST_APPROVED، والاستعادة BACKUP_RESTORE_APPROVED، بقيمة true بعد اعتمادها فقط.

الأوضاع اليدوية:

1. **init-drive** بعد موافقة BACKUP_DRIVE_SETUP_APPROVED=true: يتحقق من الحساب وينشئ مجلد **Adwaa PostgreSQL Encrypted Backups** في My Drive، أو يعيد استعمال المجلد المخصص المعلّم الذي أنشأه هذا التطبيق سابقًا. لا يبحث بالاسم عن المجلد القديم ولا يعدله. يطبع معرف المجلد الجديد فقط لوضعه في متغير البيئة؛ لا رموز. إذا كانت نتيجة إنشاء المجلد غير معروفة، يُعاد فحص marker عند المحاولة التالية، لا اختيار مجلد قديم بالاسم.
2. **preflight**: تحقق الحساب والملكية وعدم المشاركة وقدرة الكتابة والمساحة، وTLS/source PG17 وapp_state؛ لا dump أو ملف Drive جديد. المجلد يجب أن يحمل marker أضافته خطوة setup للتطبيق الجديد، وإلا يُرفض بدل تعديل المجلد.
3. **backup**: snapshot/dump وتشفير ورفع وقراءة من Drive واستعادة ومقارنة. Google الحقيقي وPostgreSQL الحقيقي يحتاجان اعتمادًا قبل التجربة؛ لا تستخدم بيانات عملاء في معاينة عامة.
4. **restore**: يعيد اختبار أحدث complete backup عمرها أقل من 48 ساعة، إلى الهدف المعزول فقط، بلا تغيير للمصدر.
5. **retention-plan**: يعرض عدد الملفات الجديدة المعلّمة الأقدم من 30 يومًا **دون حذف** أو أسماء عملاء/محتوى. النسخ القديمة خارج المجلد والـnamespace لا تدخل الخطة.

Google credentials لا تمر إلى حاوية pg_dump أو هدف الاستعادة. مصدر PostgreSQL يحتاج دور قراءة لجميع الجداول وBYPASSRLS وصلاحيات قراءة LO، direct أو session pooler على 5432 وverify-full؛ لا transaction pooler ولا enable-row-security لتجاوز جداول ناقصة. لا تخلق هذه المهمة دورًا أو تغيّر صلاحيات الإنتاج. لا تتوفر تلك الأسرار هنا، وقراءة أسماء GitHub Secrets كانت مرفوضة 403 في المراجعة السابقة؛ لا ندعي تجهيز الربط.

## الساعة 3 صباحًا والاحتفاظ 30 يومًا — معطلان

[activation-plan.json](activation-plan.json) يسجل **00:00 UTC يوميًا = 03:00 Asia/Riyadh**، بلا DST، وretention_days=30. هذا ملف خطة وليس trigger. لا حدث schedule في workflow؛ اختبارات تمنع وجوده الآن. حتى إضافة cron بالخطأ لا تكفي: السكربت يرفض الحدث دون BACKUP_SCHEDULE_APPROVED وBACKUP_PRODUCTION_RESTORE_VERIFIED وموافقة احتفاظ Drive.

قيم BACKUP_SCHEDULE_APPROVED وBACKUP_PRODUCTION_RESTORE_VERIFIED وBACKUP_DRIVE_RETENTION_APPROVED ثابتة false في workflow الحالي. بعد نجاح تجربة الإنتاج ورفعها وتنزيلها واستعادتها مع دليل موثق، ثم **موافقة المالك الصريحة المنفصلة**، يأتي تعديل مراجَع لإضافة cron `0 0 * * *` وتمكين البوابات. GitHub cron أفضل جهد وقد يتأخر خصوصًا أول الساعة؛ ليس ضمانًا للتنفيذ عند الثانية المحددة، ولا ننشئ خدمة مدفوعة لتحسين ذلك دون موافقة.

Drive لا يوفر lifecycle/TTL مماثلًا لـS3. دالة الاحتفاظ المستقبلية موجودة لكنها معطلة: لا تعمل إلا بعد إنتاج restore gate، ونجاح **الاستعادة الحالية** لنسخة حديثة أقل من 48 ساعة، وموافقة حذف مستقلة. تعمل على مجموعات الملفات **الجديدة التي أنشأها التطبيق في المجلد المخصص**، بمعرف نسخة وتاريخ إنشاء فعلي أقدم من 30 يومًا، مع إعادة التحقق من المالك/المجلد/marker لكل ملف. لا تحذف المجلد أو النسخ القديمة أو JSON legacy أو الملفات غير المعلّمة، وتبقي النسخة الحديثة المثبتة. تحذف الملفات المنتهية نهائيًا مستقبلًا بعد الموافقة؛ trash وحده قد يبقيها 30 يومًا إضافيًا ويستهلك المساحة. **لم تُستدع أي عملية حذف أو trash أو تعديل فعلية في هذه الجولة**؛ اختبارات الحذف تستعمل بيانات وخدمة وهمية فقط.

لا تنشئ approval variable true أو حدث cron الآن. إن لم تُعتمد سياسة حذف الملفات الجديدة لاحقًا، تبقى الخطة قراءة فقط وقد تتراكم النسخ؛ لا يجوز الادعاء باحتفاظ آلي 30 يومًا عند تعطيل الحذف.

## المساحة والتكاليف والقيود

- Google Drive API لا يفرض عادة رسومًا منفصلة للطلبات ضمن الحصص، لكنه يفرض حدود طلبات/رفع وقد يرفض 403/429. هذه ليست ضمانًا لعدم تغير سياسة Google. لا موارد مدفوعة أو اشتراك جديد أُنشئ.
- مساحة الحساب الشخصي المجانية المعتادة 15GB مشتركة مع Gmail وPhotos؛ **لم تثبت المساحة المتبقية لهذا الحساب** عبر connector الحالي. preflight الفعلي يستعلم storageQuota ويرفض الحساب الخطأ/الحد غير المؤكد، ويشترط قدرة ميزانية 31 نسخة تقريبًا (30 يومًا ونسخة قيد الإنشاء) ضمن المساحة المتاحة للـnamespace، مع مساحة فعلية لنسخة جديدة. رفع الحزمة يرفض حجمًا يتجاوز الميزانية المعتمدة. لا تُحذف الرسائل أو الصور أو ملفات قديمة لتحرير مساحة.
- تقدير السعة: 31 × حجم الحزمة المشفرة اليومية + الملفات الأخرى بالحساب + أجزاء المحاولات غير المكتملة. مثلًا 50MiB يوميًا ≈1.6GiB، بينما 1GiB يوميًا يتجاوز المساحة المجانية المعتادة. Google One أو غيره يحتاج موافقة تكلفة إذا لزم؛ لا يُشترى تلقائيًا.
- Actions يعيد الاستعادة لكل backup حاليًا، فيستهلك دقائق وذاكرة ونقلًا. تختلف مجانية الدقائق بحسب المستودع والخطة؛ لا نفترضها للجميع. الهدف الحالي memory=4GiB وtmpfs=4GiB للبيانات و4GiB للأرشيف، بلا شبكة. حدود المصدر/الحزمة تمنع تضخمًا غير معتمد، ولا تضمن توافق امتدادات Supabase؛ يجب اعتماد صورة PG17 متوافقة مع supabase_vault وغيرها. لا يُحذف امتداد أو مالك/دور لفك فشل الاستعادة.
- رموز OAuth قد تُلغى أو تنتهي، والحصة قد تمتلئ؛ تنبيه GitHub Actions/Issue الموجود باقٍ دون diagnostics حساسة. لم يُختبر تنبيه فعلي أو grant جديد في هذه الجولة.
- JSON السابق وdump الجديد ليسا نسخ ملفات Supabase Storage. آخر inventory سابق أظهر 0 buckets/objects؛ يعاد التحقق قبل التفعيل، وتحتاج الملفات عند إضافتها نسخًا واستعادة منفصلين معتمدين. إعدادات Auth/SMTP/Edge/Vault وخدمات الإرسال لا تُفترض مغطاة بالأرشيف وحده.

## الاختبارات والدليل

اختبارات آلية مصطنعة: التشفير والتلاعب والحصة والحساب الخطأ ومجلد مشترك/قديم ورفض OAuth واسع أو غير مؤكد، ضياع رد الرفع وإعادة المحاولة دون ملف إضافي، رفض overwrite، القراءة وفحص SHA، الاحتفاظ المعطل وصون legacy، رفض حذف ملف منقول خارج المجلد، وخطة الوقت 3 صباحًا المعطلة. اختبار التكامل ينشئ dump فعليًا لستة جداول مالية مصطنعة وكائن كبير، ويمرره **مشفرًا عبر Drive service double** ثم ينزله ويستعيده في PostgreSQL مستقل ويقارن المصدر بعده. هذا ليس اختبار Google OAuth/Drive حيًا أو نسخة إنتاج.

الحالة: المسودة تدعم Drive، **غير مفعلة وغير معتمدة إنتاجيًا**. المطلوب للربط: عميل OAuth مستقل وgrant offline للحساب المحدد في Secrets، إعداد المجلد الجديد، ميزانية مساحة فعلية، اتصال PG مخول وهدف متوافق، ثم تجربة إنتاج ناجحة وموافقة تفعيل. المجلد والنسخ السابقة باقية دون تغيير، وPR #164 غير ممسوس.
