## اختبار Storage عبر API الرسمي

المسار: backup-storage-api-test.yml → storage_api_check.py → storage_api_restore.py.
يستخدم الحزمة المعتمدة أعلاه، مع تثبيت بصمات أجزائها الأربعة في الكود.
لا يصدّر المصدر ولا ينشئ مجلد Drive ولا يحمل بيانات اتصال PG أو مفتاح Storage
للإنتاج. يلزم اعتماد SHA بواسطة مراجع production-backup.

الضوابط:

- رفض مرجعي الإنتاج قبل أي HTTP، وطلب مرجع هدف مطابق لتأكيد مستقل.
- HTTPS إلى `<ref>.supabase.co/storage/v1/` فقط، مع TLS ودون redirects.
- مفتاح backend للهدف فقط؛ legacy JWT يجب أن يحمل ref الهدف وservice_role.
- تأكيد أن المشروع جديد ومخصص للاسترداد، تحت ملكية أضواء الشرق وبوصول محدود،
  وليس مشروع عميل أو مشروعًا يشترك مع تطبيق حي. Storage API وحده لا يثبت
  عضوية فريق Supabase أو غياب سياسات مخصصة؛ يؤكد المالك ذلك عند اعتماد الهدف.
- التحقق من SHA-256 وGCM ثم كل أعضاء TAR والبصمات في RAM مختومة قبل أي كتابة.
- رفض أي هدف يحتوي buckets، حتى لو بدت فارغة. لا استبدال أو upsert أو DELETE.
- إنشاء كل buckets **خاصة** ولو كانت عامة بالمصدر، ثم رفع كل المسارات، وتنزيل
  كل ملف عبر API ومقارنة حجمه وبصمته، وجرد recursive/paginated لكشف الفقد والزيادة.
- الفشل يُبقي الملفات الجزئية في الهدف ويمنع اعتماد النجاح؛ إعادة المحاولة لا
  تحذفها أو تتخطى شرط الهدف الفارغ. يلزم تقييم المالك أو هدف اختبار جديد.

إعادة الرفع عبر API تُنشئ IDs/versions/timestamps جديدة؛ لا يدّعي الاختبار تطابق
storage.objects بعد إعادة الرفع. المخطط والبيانات الوصفية الأصلية محفوظة في
SQL المشفر وثبتت استعادتها مستقلًا. اختبار API يثبت قابلية إعادة خدمة المحتوى
بالأسماء وبالبصمات نفسها داخل مشروع معزول، دون كشفه للعامة.

**المتطلب غير المتاح حاليًا:** لا يوجد اتصال/اعتماد متاح لمشروع Supabase اختبار
معزول في الأدوات أو الإعدادات المكتشفة. لا توجد صلاحية Management API لإنشائه؛
ولم أُنشئ مشروعًا مدفوعًا أو أستخدم مشروع إنتاج بديلًا.

يضيف المالك من واجهة GitHub → Environment production-backup:

| النوع | الاسم | المصدر |
|---|---|---|
| Variable | BACKUP_STORAGE_RESTORE_PROJECT_REF | مرجع مشروع الاختبار المخصص فقط |
| Variable | BACKUP_STORAGE_RESTORE_CONFIRMED_PROJECT_REF | المرجع نفسه بعد تأكيد العزل والملكية |
| Secret | BACKUP_STORAGE_RESTORE_API_KEY | backend key لهذا المشروع المعزول فقط |

لا تُرسل قيمة المفتاح بالمحادثة أو تضعها في Git. التشغيل لا يطلب استبدال أي
سر من الأسرار الأصلية الخمسة عشر. النتيجة المقبولة STORAGE_API_RESTORE_VERIFIED
وobjects_verified=31 وtest_buckets_private=true؛ لا يكفي نجاح اختبارات المحاكاة.

## التشغيل اليومي والمراقبة — مجهز دون تفعيل

- database-backup.yml ما زال workflow_dispatch فقط وmain فقط، ضمن البيئة المحمية.
  يبني صورة PG17/Vault نفسها محليًا إلى image ID ثابت لكل تشغيل، فلا يعتمد على
  image tag متغير أو صورة محلية من تشغيل سابق. runtime.py يتحقق من المجلدين
  المعتمدين ويستخدم تقديرات القياس السابقة إذا لم توجد متغيرات اختيارية.
- أُزيل التعارض الذي كان يشترط تفعيل retention لتشغيل الجدولة رغم منعه عالميًا.
  تظل حماية الحذف قائمة؛ تفعيل جدول لاحقًا لا يعطي إذن حذف.
- backup-health.yml منفصل، للقراءة فقط، دون PG أو مفاتيح فك تشفير: يفحص عمر
  اللقطة من backup_id (30 ساعة)، وrestore-ok، وحجم وبصمة الأجزاء من metadata
  Drive. ليس بديلًا عن تنزيل وفك تشفير واستعادة دورية فعلية.
- backup-watchdog.yml مستقل عن بيئة النسخ وأسرارها: يكتشف غياب التشغيل المجدول
  أو فشله أو تعليق الموافقة/التنفيذ أكثر من ساعتين أو نجاح مشروع واحد فقط.
  التشغيل الجاري ضمن مهلة البداية لا يُعد شهادة نجاح نسخة.
- notify.py يستخدم تذكرة GitHub واحدة للمالك، مع رمز ثابت ورابط تشغيل، دون
  رسائل أخطاء أو أسماء عملاء أو أسرار، ويمنع تكرار التنبيه لنفس التشغيل.
  اختبارات النقل محاكاة؛ لم تُرسل رسالة اختبار حية ولم يُثبت تسليم إشعاراتها.

الخطة غير المفعلة: نسخة 00:00 UTC = 03:00 الرياض؛ health وwatchdog كل 6 ساعات
(التعبير المقترح `30 */6 * * *`). قد يصل اكتشاف النسخة المتأخرة إلى 36 ساعة
بحسب توقيت الفحص، بينما فشل تشغيل مكتمل يُبلّغ من مسار الفشل مباشرة عند عمله.
GitHub cron غير مضمون الدقة. تعطيل Actions كلها أو انقطاع GitHub قد يعطل
المراقبين معًا؛ يلزم مراقب خارجي مستقل إذا أُريد كشف هذا السيناريو أيضًا.

**عائق الأتمتة:** فحص API إعداد البيئة أكد required_reviewers وقيود فروعها.
الموافقة مطلوبة لكل job؛ cron لا يتجاوزها ولن يصبح تلقائيًا بالكامل مع السياسة
الحالية. لم أغيّرها. قبل التفعيل يختار المالك سياسة مراجعة صريحة تسمح بالنسخ
المجدول المعتمد على main وتحافظ على مراجعة الاستعادة والتهيئة اليدوية؛ أو يبقي
الموافقة اليومية. لا تُنقل الأسرار إلى نطاق أوسع لتجاوز هذه الحماية.

قبل أي موافقة نهائية يلزم أيضًا اختبار تسليم التنبيه الحقيقي، وhealth حي،
والتحقق من قيود main ومتغيرات الموافقة والسعة، ثم مراجعة فرق تفعيل مستقل.
activation-plan.json وBACKUP_SCHEDULE_APPROVED وBACKUP_PRODUCTION_RESTORE_VERIFIED
ما زالت غير مفعلة؛ لا توجد schedule triggers في أي من المسارات الثلاثة.

## التشفير والاحتفاظ والاسترداد

AES-256-GCM بمفتاح 32 بايت مستقل لكل مشروع، nonce عشوائي لكل جزء، وAAD يربط
المشروع/backup_id/الجزء. SHA-256 يفحص النقل؛ GCM يفحص المصادقة. لا تُكتب
complete إلا بعد الحزم الأربع، ولا restore-ok إلا بعد الاستعادة الكاملة.
لا plaintext في Git أو Actions artifacts؛ البيانات المستعادة في tmpfs، واختبار
API يفكها في memfd مختوم ويمسحها بإغلاق العملية. لا تتبع redirects للأسرار.

كل النسخ القديمة محفوظة. 30 يومًا هدف تخطيط سعة، **ليس TTL ولا إذن حذف**.
التقديران الحاليان 64MiB/يوم لـCore و256MiB/يوم لـPortal؛ حد 31 يومًا للتقديرين
نحو 9.69GiB. الحجم المشفر الفعلي الحالي نحو 73.8MB معًا للّقطة الواحدة، وقد
يزداد. لا نعد بسعة مجانية غير محدودة؛ نقص المساحة يوقف النسخ وينبه ولا يحذف
أو يختصر البيانات. يراجع المالك السعة أو الأرشفة المشفرة خارج GitHub مستقبلًا.

في حادث استرداد: احفظ المصدر والنسخ، حدد المشروع واللقطة، استرجع **المفتاح
الأصلي الموافق** من حفظ مستقل مشفر، افحص complete والأجزاء وSHA-256 ثم GCM،
واستعد في هدف جديد معزول وقارن البيانات والمنح والصفوف والتسلسل وStorage.
لا تستخدم restore فوق الإنتاج. تشغيل تطبيق جديد وربط Auth/Storage/DNS/OAuth
وكلمات المرور يحتاج خطة تحويل مستقلة واعتمادًا؛ لا تنقل بيانات عميل إلى مشروع عميل آخر.

## الاعتماد المكشوف — خطة دون تنفيذ

المؤكد من المحادثة: Google OAuth Client Secret ظهر في صورة. لا دليل هنا يثبت
تسرب Refresh Token أو مفاتيح تشفير البيانات؛ لا ندّعي سلامتها من كل مصدر ولا
ندوّرها عشوائيًا. لم أغيّر أيًا منها.

1. بعد إذن المالك وفي Google Cloud، دوّر السر للـClient ID **نفسه**. إذا أتاح
   سرين، احتفظ بالقديم مؤقتًا؛ تغيير Client ID قد يفقد التطبيق رؤية ملفات drive.file.
2. حدّث ملف OAuth الأصلي محليًا خارج Git، ثم شغّل الفحص/المزامنة الموجودة في
   C:\Adwaa-Backup. لا تفتح الرمز أو تنسخه للمحادثة. الأداة تجدد فقط عبر نقطة
   Google الرسمية وتستخدم stdin مع gh secret set دون طباعة القيم.
3. أثبت OAUTH_LOCAL_OK ثم GITHUB_OAUTH_SYNC_OK وفحص Drive محمي من runner،
   مع الوصول إلى **المجلدين والنسخ السابقة**، قبل تعطيل السر المكشوف القديم.
   إذا رفض Google التجديد، أعد تفويض العميل نفسه؛ لا تفترض أن الرمز سيبقى صالحًا.
4. لا تدوّر مفاتيح تشفير البيانات لمعالجة تسرب سر OAuth. يجب الاحتفاظ بمفاتيح
   كل الأرشيفات القديمة؛ الصيغة الحالية لا تحمل key_id، لذا يلزم تطوير keyring
   واختباره قبل أي تدوير مستقبلي لمفتاح البيانات. لا توجد موافقة لتدويره الآن.

السر المحلي وعميل Google Cloud ليسا متاحين للأدوات الحالية لتدوير رسمي آمن؛
هذه خطوة مالك حصرية بعد إذنه، وليست إجراءً نفذته أو اختبارًا نجح.
