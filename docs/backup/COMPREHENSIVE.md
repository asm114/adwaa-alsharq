# النسخ متعدد المشاريع وStorage — تطوير محلي غير مفعّل

هذا المستند يحل محل وصف «قاعدة واحدة وStorage خارج النطاق» في دليل التشغيل السابق، ولا يعلن تحققًا إنتاجيًا أو اكتمال تشغيل خدمة Supabase بعد كارثة. لا تفعيل جدولة أو حذف. لا تُرفع هذه التغييرات قبل اعتماد المالك.

|---|---|---|
| core | pgdvlklpyrvmwzitsmbw | إعداد الإنتاج وapp_state في التطبيق |

لم نفحص حساب المالك أو كتالوج PostgreSQL الحي للبوابة لغياب بيانات اتصالها. قد تستعمل الإدارة هذا المشروع أيضًا بوصف Staging؛ هذا لا يغيّر أن البوابة العامة تشير إليه. يتطلب التشغيل BACKUP_CONFIRMED_PROJECT_REF مطابقًا حرفيًا للهدف، ثم TLS واسم مستخدم pooler المرتبط بالمشروع وفحص الجداول: app_state للإدارة، وcustomer_portal_resort_info وcustomer_portal_unavailable_periods وcustomer_portal_admins للبوابة. لا تسمح الأداة بإدخال مشروع ثالث أو إعادة توجيه HTTP أو مضيف API عشوائي.

## المحرك المشترك والتغطية

- لا محرك dump أو تشفير أو Drive موازٍ: tools/backup/backup.py وdrive_store.py نفسيهما يقرآن الهوية المحددة من targets.py. الاختيار يتم عند بدء العملية، فلا تُبدل أهداف داخل عملية واحدة.
- workflow اليدوي matrix لهدفين منفصلين، fail-fast=false، وأسرار اتصال وتشفير ومجلدات وصور استعادة مستقلة. لا نجاح لتشغيل workflow كامل إذا فشل أحدهما. لا schedule trigger. لا يُنفذ حذف ضمن المسار الشامل حتى عند تعيين متغير اعتماد بالخطأ.
- dump كامل لكل قاعدة، بما فيها Auth وStorage metadata إن سمحت الصلاحيات. يحتفظ بالفروق بين app_state والجداول المنفصلة دون توحيدها. بصمات كل الصفوف تحفظ كل قيم JSON والمالية دون اختيار أعمدة أو إعادة حسابها.
- صيغة جديدة format=2: database.enc وroles.enc وverification.enc وstorage.enc ثم complete.json. صيغة format=1 قابلة لاختبار الاستعادة القديمة لكن لا تجتاز health بوصفها نسخة قاعدة وملفات. لا تحويل صامت ولا حذف للقديم.
- أرشيف Storage هو TAR مشفر متدفق بـAES-256-GCM قبل القرص؛ أعضاؤه معرفات تسلسلية فقط، لا أسماء عملاء أو مساراتهم. verification.enc يحوي جرد buckets/object metadata ومطابقة المسارات والنسخ والأحجام وSHA-256 للبايتات. manifest العام لا يحتوي أسماء الملفات أو بيانات العملاء.
- الجرد من storage.buckets وstorage.objects باتصال يتجاوز RLS ومخوّل للقراءة؛ لا استنتاج لجرد كامل من قائمة public محدودة. لا صفحات API للملفات يمكن أن تُنسى؛ استعلام SQL غير محدود بـLIMIT، مع حد عدد معتمد يفشل بدل القطع. تُقارن قائمة buckets وإعداداتها مع GET API، وتُنزل كل البايتات بمصادقة مع التحقق من الحجم.
- لا POST/PUT/PATCH/DELETE في Storage source؛ اعتماد backend قد يملك قدرات أعلى من المستخدم فعليًا، لكن هذا الكود لا يستخدمها. لا إعداد RLS أو جعل bucket عامة أو إنشاء دور في الإنتاج.

## الاتساق والموارد

جرد الملفات من لقطة SQL نفسها التي تُستخدم للـdump. بعد الالتقاط تُقارن نسخة جديدة من الجرد بكل metadata المستقرة وversion وupdated_at والحجم. تغير أو فقد أو نقص صلاحية أو انقطاع يمنع complete، ولا يُتخطى الملف. يُستثنى last_accessed_at المتغير مع القراءة؛ لا تُتجاهل نسخة المحتوى أو وقت تعديله. يتطلب وجود version وupdated_at وmetadata.size، وإلا يفشل المصدر لإيضاح عدم دعم مخططه بدل تخمينه.

لا توجد لقطة ذرية موزعة بين قاعدتي المشروعين وObject Storage. هذه مقارنة نافذة ثبات قبل/بعد، لا ضمانًا ضد تعديل خارجي لا يحدّث metadata. يجب اعتماد نافذة تحقق مناسبة وفحص روابط البيانات بين المشروعين قبل التشغيل الحقيقي؛ لا يوقف الكود كتابات الإنتاج. النسخة تسجل capture_started/capture_finished مشفرين لكل قاعدة.

افتراضيًا حد قاعدة 1GiB وحد بايتات Storage 1GiB وحد 100000 كائن، مع سقف تنزيل 2GiB لكل جزء مشفر في ناقل Drive الحالي. لا يجزّئ ملفًا أكبر تلقائيًا. يلزم اعتماد السعة ومراعاة overhead للـTAR وملفات الاستعادة/الفك المتزامنة في tmpfs (4GiB) وصورة امتدادات PG17 المتوافقة لكل مشروع. إذا كانت الأحجام أكبر تُصمم سعة/تجزئة وتُختبر في تعديل منفصل؛ لا رفع الميزانية عشوائيًا. لا ضمان أن المشروعين يعملان بـPG17 حتى فحصهما الحقيقي؛ اختلاف الإصدار يفشل ولا يغيّر الإنتاج.

## الاستعادة المعزولة — ما تم اختباره وما لم يتم

لكل هدف استعادة مستقلة في Docker network=none بلا منافذ أو بيانات اعتماد الإنتاج. يُنزّل المحتوى من ناقل Drive، وتُفحص الأحجام وSHA-256 ثم GCM قبل استعماله. استعادة SQL تقارن المخطط والأدوار والصلاحيات والتسلسل وكل صف وكائن كبير. storage.enc يفك إلى tmpfs فقط، ثم يعيد بناء كل ملف داخل الحاوية بأسماء داخلية مقيدة، ويرفض أعضاء TAR غير المتوقعة/الروابط/التكرار/المسارات الخبيثة. تُقارن البايتات عند النقل وبصمة الملف المعاد بناؤه بالفعل. bucket/object metadata موجودة في SQL المستعاد وفي الجرد المشفر.

**الحد المتبقي صريح:** storage_files_verified=true تعني تطابق بايتات الملفات وإعادة بنائها المعزولة، وليست إثبات أن خدمة Supabase Storage الرسمية أُعيد تشغيلها وربطت backend file/S3 وبنسخ الكائنات على نحو صحيح. النتيجة تسجل storage_service_restore_verified=false. اختبار تشغيل الخدمة الرسمية المتوافقة واستيراد/ربط الكائنات وتحقق التنزيل عبر API في بيئة اختبار منفصلة ما زال بوابة قبل إعلان استرداد تشغيلي كامل. لا تستعمل CLI الحالي لتحميل ملفات إلى الإنتاج، ولا تغيّر metadata الإنتاج لتحقيق ذلك.

لا تشمل هذه الحزمة وحدها كود Edge Functions المنشور وإعدادات SMTP/DNS/OAuth ولوحة المنصة وأسرارها؛ اجردها وأمّن إجراءات استردادها بصورة منفصلة دون وضع أسرار داخل dump metadata غير مشفر أو GitHub.

## GitHub Environment: production-backup

1. أنشئ/راجع Environment من Settings → Environments → production-backup، واضبط مراجعين وقيود main ومنع self-review حسب خطة الحساب. لا تنشئها بلا حماية لمجرد تجاوز بوابة.
2. أضف القيم من محرر Secrets الآمن فقط؛ لا رسالة دردشة أو Issue أو shell history أو ملف مستودع. لا نحتاج استعراض قيمها في تقرير. لم ننشئ أو نعدّل Secrets هنا.
3. الأسماء السابقة المفردة BACKUP_PGHOST وما شابه لا تُستخدم في matrix الجديدة: انقلها عبر الواجهة الآمنة إلى أسماء core فقط دون افتراض أنها صالحة للبوابة. لا تلصق كلمة مرور داخل PGHOST.

### أسرار مشتركة

BACKUP_DRIVE_CLIENT_ID وBACKUP_DRIVE_CLIENT_SECRET وBACKUP_DRIVE_REFRESH_TOKEN من التفويض نفسه وبنطاق drive.file فقط، وحالة OAuth مناسبة للاستمرار. رمز المتصفح/ملف اتصال Drive لا يغني عن وصول المشغل الفعلي.

### أسرار مستقلة — استبدل {TARGET} بـCORE ثم PORTAL

| الاسم | المطلوب |
|---|---|
| BACKUP_{TARGET}_PGHOST | direct أو Session Pooler الخاص بالهدف على 5432 |
| BACKUP_{TARGET}_PGUSER | حساب له قراءة جميع الجداول والـLO والتسلسل وBYPASSRLS |
| BACKUP_{TARGET}_PGPASSWORD | كلمة المرور لهذا الحساب، دون طباعتها |
| BACKUP_{TARGET}_CA_PEM | CA رسمية/موثوقة لاتصال verify-full |
| BACKUP_{TARGET}_ENCRYPTION_KEY | 32 بايت عشوائية Base64؛ مفتاح مستقل ونسخة استرداد مشفرة خارج GitHub وDrive |
| BACKUP_{TARGET}_STORAGE_API_KEY | backend credential يمكنه قراءة جميع buckets/objects للهدف؛ لا anon أو publishable |

يفضل اعتماد مخصص بأقل صلاحيات قراءة ممكنة، لكن إنشاء دور/سياسة جديدة غير مصرح به هنا. إذا لم يوجد إلا service_role أو sb_secret فهو اعتماد مرتفع الصلاحية رغم أن الأداة تقرأ فقط؛ يجب اعتماد استخدامه وتقييد الوصول إليه في Environment وعدم إرساله إلى حاويات dump/restore أو logs. لا تتجاوز نقص الصلاحيات بتغيير RLS أو استخدام قوائم عامة ناقصة. لا تعتمد غياب بعض buckets كنجاح.

### متغيرات مستقلة — استبدل {TARGET} بـCORE ثم PORTAL

- BACKUP_{TARGET}_CONFIRMED_PROJECT_REF: المرجع في الجدول أعلاه بعد اعتماد المالك، لا كلمة مرور.
- BACKUP_{TARGET}_DRIVE_FOLDER_ID: مجلد خاص معلّم لكل مشروع؛ لا تبدّل المجلدين أو تعتمد مجلد ملف التجربة/JSON القديم. init-drive يحتاج موافقة إنشاء مستقلة ويطبع معرف المجلد فقط.
- BACKUP_{TARGET}_DRIVE_ESTIMATED_DAILY_BYTES: تقدير حزمة القاعدة والملفات كاملة مع الهوامش، لا حجم database.enc فقط.
- BACKUP_{TARGET}_RESTORE_IMAGE: صورة معتمدة متوافقة مع امتدادات الهدف ومثبتة digest.
- BACKUP_{TARGET}_MAX_DATABASE_BYTES وBACKUP_{TARGET}_MAX_STORAGE_BYTES: سقوف معتمدة؛ الافتراضي 1GiB لكل منهما.

المشتركة: BACKUP_DRIVE_ACCOUNT، BACKUP_ALERT_ASSIGNEE، وبوابات التنفيذ/السعة/الاستعادة/إعداد المجلد. تبقى BACKUP_SCHEDULE_APPROVED وBACKUP_PRODUCTION_RESTORE_VERIFIED وBACKUP_DRIVE_RETENTION_APPROVED ثابتة false؛ لا تشغيل يومي أو حذف. يُمكن تشغيل فحص health لكل هدف يدويًا لاحقًا لكنه ليس مراقبًا مستقلًا ولا شهادة استعادة API للخدمة.

## خطوات اختبار إنتاجي لاحق — لم تُنفّذ

1. اعتماد هوية المشروعين وصلاحيات القراءة والسعة ونسخ المفاتيح، وفحص source PG version وصور الاستعادة. لا تعدّل المشروعين لتلائم الاختبار.
2. تشغيل preflight لكل هدف يدويًا من بيئة محمية ذات TCP/API صالحين، مع حقن الأسرار. لا dump أو رفع ملفات أو كتابة مصدر في هذا الوضع.
3. بعد موافقة تشغيل النسخ ورفعها، backup لكل هدف: SQL قراءة فقط + GET Storage، ورفع الحزم المشفرة إلى Drive ثم تنزيلها واستعادتها إلى Docker فقط. لا complete قبل اكتمال أربعة أجزاء؛ لا restore-ok قبل تطابق SQL والبايتات. نجاح الهدفين شرط لقبول التشغيل.
4. مراجعة تقرير مشفر للأعداد والبصمات وفترات الالتقاط والروابط بين القاعدتين، ثم إكمال اختبار خدمة Storage الرسمية المعزولة. لا تُظهر أسماء الملفات أو بيانات العملاء في logs أو screenshots.
5. اختبار أخطاء المصادقة/المساحة/فقد الملف/إنذار فشل ومراقبة غياب تشغيل. ثم مراجعة واعتماد منفصلان لأي دمج/جدولة/احتفاظ. لا تفعيل تلقائي بمجرد نجاح CI الاصطناعي.

## اعتماد تهيئة المجلدين فقط

`init-drive` يحتاج `BACKUP_DRIVE_SETUP_APPROVED=true` و`BACKUP_COST_APPROVED=true` فقط؛ لا يحتاج `BACKUP_EXECUTION_APPROVED` ولا يمنحه. مسار التهيئة يبقي مطابقة SHA ومراجعة production-backup والوضع الثابت، ولا يمرر إذن التنفيذ العام إلى مهمة إنشاء المجلدين. `backup` و`restore` يبقيان مقيدين بإذن التنفيذ العام والبوابات السابقة. لا تشغيل للتهيئة بمجرد رفع التعديل: يجب اعتماد SHA الجديد ثم إجراء مراجعة التشغيل بصورة منفصلة.
