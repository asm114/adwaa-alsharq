# مراجعة تحديث واجهة أضواء الشرق

التاريخ: 28 أكتوبر 2026.
الفرع: `design/app-interface-20261028`.
المصدر: أحدث `origin/main` عند `6fc321e`، نسخة مستقلة عن أي عمل سابق غير مكتمل.

## ما تغير

- توحيد ألوان وعناصر واجهة الإدارة، الحقول، الأزرار، حالات التركيز والخطأ والتعطيل، مع الحفاظ على هوية الأخضر.
- تنظيم نموذج الحجز إلى أقسام واضحة، مع شريط انتقال داخل النموذج وحفظ ظاهر دائمًا. لا إخفاء للحقول أو استبدال لمسار الحفظ.
- تنظيم الحاسوب بقائمة جانبية والجوال بشريط سفلي، وتنسيق حقول المصروفات والنماذج المشتركة.
- ربط تسميات الحقول بعناصرها وإضافة أمثلة إدخال للاسم والجوال والملاحظات.
- توثيق العناصر الفعلية في DESIGN.md وملف التصميم المرافق.

## الملفات

- `index.html`: عنوان الواجهة، التسميات، أمثلة الإدخال، إصدار مشغل العرض.
- `admin-workspace.js`: إصدار تحميل طبقة العرض.
- `admin-workspace-core.js`: انتقال بين أقسام الحجز فقط؛ لا وصول جديد للبيانات أو تغيير في الحفظ.
- `admin-workspace.css`: التنسيق المتجاوب وحالات عناصر التحكم.
- `DESIGN.md` و`.impeccable/design.json`: توثيق التصميم.
- `accounting-notes.js`: إتاحة معالج الحفظ الموجود لإعادة استخدامه بعد استبدال نموذج الصيانة.
- `maintenance-open-cost.js`: ربط نماذج الصيانة بمعالج الأخطاء وحفظ معرّف الدفعة قبل انتظار الحفظ لمنع التكرار عند إعادة المحاولة.
- `tests/maintenance-retry.test.mjs`: ثلاثة اختبارات تنفيذ لمعالجة رفض الحفظ وإعادة المحاولة ومنع الضغط المكرر.
- `tests/accounting-notes.test.mjs`: تحديث إصدار مورد العرض المتوقع.
- هذا التقرير.

## التحقق الفعلي

- `node --test tests/*.test.mjs tests/*.test.js`: 333 ناجحًا، صفر فاشل.
- `node --check admin-workspace-core.js` و`admin-workspace.js`: ناجح.
- `git diff --check`: ناجح.
- فحص Impeccable مرة واحدة على CSS وJS: ملاحظة side-tab في سطر موجود سابقًا؛ عُدّل الحد من 3px إلى 1px. لم يُعد الفحص بعد الإصلاح.
- فحص بصري في Chromium لواجهة فعلية معزولة على الحاسوب 1363×936، وداخل إطار عند 390 و320 بكسل؛ ليست تجربة على أجهزة فعلية.
- عرض الصفحة وعميل العرض كلاهما 320px؛ لم يظهر تمدد أفقي للصفحة في الحالة المقاسة.
- انتقال «الإقامة» في الحاسوب يحدد القسم ويركز حقل التاريخ. انتقال «الدفع» في الجوال يحدد القسم ويركز حقل العربون، مع بقاء الحفظ ظاهرًا.
- محاكاة متصفح باستخدام بديل Supabase في الذاكرة وبديل مزامنة Portal: نجح 19 تأكيدًا، منها إنشاء حجز 1200 وعربون 500، دفعة إضافية 200، تعديل، التنقل، مصروف100، وعدم تكرار الصيانة وإعادة المحاولة.
- **بعد إصلاح مسار الصيانة نجحت التأكيدات الـ19 كاملة**، بما فيها «لا أخطاء تنفيذ غير معالجة»، أثناء حقن فشل الحفظ وإعادة المحاولة. كان النموذج المستبدل يفقد guardedSubmit؛ أُعيد استخدامه، وحُفظ paymentId قبل await. اختبار مستقل يؤكد أن إعادة المحاولة تجري كتابة ثانية فعلية مع بقاء دفعة ومصروف واحدين ورصيد -700 ومتبقي500. هذه محاكاة معزولة وليست تجربة إنتاج حية.
- مراجعة مستقلة للصور والمصدر طلبت إصلاح تحديد القسم في صف الحاسوب المشترك؛ أُصلح وأُعيد تصويره، ثم اعتُمد الإصلاحان المقيمان فقط. لا ادعاء باعتماد جميع شاشات التطبيق.

## الحدود والحالة

لا اختبار حي لقاعدة البيانات أو Portal أو تسجيل الدخول، ولا كتابة في الإنتاج. لم تتغير صيغ الحسابات أو منطق الحجوزات أو فصل Core/Portal؛ عُدّلت معالجة أخطاء حفظ الصيانة وهوية إعادة محاولة الدفعة فقط. لم يتغير أو مخطط البيانات أو الصلاحيات أو hooks أو النشر. بوابة العميل العامة خارج هذه الدفعة.

أُنشئت المعاينة من المصدر الحالي مع منع اتصال الشبكة وخدمات تجريبية؛ ملفات المعاينة مؤقتة وغير داخلة في التغييرات.

لم يُنشأ Commit، ولم يحدث Push أو Merge أو نشر. التغييرات محلية وقابلة للمراجعة قبل أي اعتماد للنشر.

## إكمال مراجعة الشاشات

فُحصت الشاشات الرئيسية التسع: الرئيسية، الحجوزات، العملاء، التقويم، المالية، الإعدادات، حول النظام، حماية البيانات، وإدارة البوابة. المراجعة لحالات ظاهرة مختارة وليست اختبارًا لكل عنصر في النظام.

- صور حاسوب للشاشات الثانوية، وصور جوال390 للعملاء والمالية والتقويم والإعدادات والحماية وإدارة البوابة.
- قياس الشاشات التسع داخل إطار320: clientWidth وscrollWidth متساويان305 بعد خصم شريط التمرير15؛ لا تمدد أفقي للصفحة في الحالات المقاسة.
- إصلاح تزاحم فلاتر التقويم بعرض تلقائي والتفاف منضبط، وتحسين تباين زري الرجوع والتحديث، وتوسيع بطاقات الحماية من ستة أعمدة إلى ثلاثة على الحاسوب وعمود واحد على الجوال.
- مراجعة مستقلة محدودة لمصدر إصلاح إعادة المحاولة وصور الشاشات: لم تجد ملاحظات مادية جديدة. لا اعتماد لسلوك الخدمات الحية.

النسخة جاهزة لاعتماد الرفع والدمج والنشر. لم تُنفّذ تلك الإجراءات، ولم يُنشأ Commit.

## اعتماد النشر

اعتمد المستخدم الرفع والدمج والنشر صراحة بعد عرض نتيجة المراجعة. أُعيد تشغيل الاختبارات قبل الرفع:333 ناجحًا، صفر فاشل. العبارات السابقة عن عدم إنشاءCommit أو النشر تصف مرحلة المراجعة المحلية قبل هذا الاعتماد. تُراجع حالة طلب الدمج والنشر في GitHub لمعرفة نتيجة التنفيذ اللاحقة.
