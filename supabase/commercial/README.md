# Commercial Supabase Migrations — ترحيلات Supabase التجارية

هذا المسار هو المصدر المعتمد مستقبلًا لإنشاء Backend جديد لعميل تجاري. لا تستخدم مجلد `supabase/migrations` القديم كمسار تركيب تلقائي للعميل؛ ذلك المجلد يحتوي تاريخ Staging/أضواء الشرق ويجب اعتباره مرجعًا تاريخيًا حتى يتم ترحيل كل جزء منه إلى المسار التجاري ومراجعته.

## الفصل بين المشروعين

التصميم التجاري الحالي يستخدم Backend منفصلين لكل عميل:

- `core/migrations` لتطبيق الإدارة و`app_state`.
- `portal/migrations` لبوابة العملاء والتشييك والوسائط والجداول العامة.

لا يطبق Migration من مسار Core على Portal أو العكس.

## قاعدة المدير

لا يوجد بريد مطور أو بريد عميل داخل Migration.

بعد تطبيق migrations، يقوم **Provisioner — أداة التجهيز** الآمنة لاحقًا بـ:

1. إنشاء مستخدم Auth للمدير في مشروع العميل.
2. تسجيل UUID المستخدم في `commercial_admins` في Core.
3. إنشاء مستخدم Auth للمدير في Portal وتسجيل UUID في `customer_portal_admins`.
4. إدخال هوية المنشأة وبيانات التواصل والعقد/الشعارات المسموح تخزينها حسب سياسة الأصول.

هذه الخطوات تستخدم بيانات اعتماد إدارية خارج GitHub. يمنع حفظ Service Role Key أو كلمة مرور العميل أو التوقيع/الختم الحقيقي في المستودع العام.

## ما تم في هذه المرحلة

### Core

`20260820001000_core_admin_and_app_state.sql`

- ينشئ جدول عضوية المدير `commercial_admins`.
- ينشئ `is_commercial_admin()`.
- ينشئ `app_state` من الصفر.
- RLS تعتمد UUID المستخدم المصادق عليه، وليس بريدًا ثابتًا.
- لا يزرع بيانات حجوزات أو عملاء أو هوية منشأة.

### Portal

`20260820001000_portal_admin_foundation.sql`

- ينشئ جدول `customer_portal_admins`.
- ينشئ `is_resort_admin()` الذي تعتمد عليه سياسات البوابة القديمة.
- لا يحتوي بريدًا ثابتًا.

`20260820002000_portal_property_info.sql`

- ينشئ جدول معلومات المنشأة دون Seed خاص بأضواء الشرق.
- لا يفتح استقبال الحجوزات تلقائيًا قبل إدخال بيانات العميل.
- الهوية الفعلية تدخل في خطوة Provisioning منفصلة.

`20260820003000_portal_images_storage.sql`

- ينشئ جدول معرض الصور وBucket الصور دون أي صورة أو تصنيف خاص بعميل بعينه.
- التصنيفات مرنة ولا تفترض مخطط منتجع محدد.
- يسمح للجمهور بقراءة Metadata الصور المرئية فقط.
- يسمح للمدير المصادق عليه بإدارة Metadata والرفع والتعديل والحذف.
- Bucket الصور عام لعرض روابط الصور، لكن لا توجد Public SELECT policy على `storage.objects` حتى لا يتحول Storage API إلى فهرس عام للملفات.
- لا يزرع ملفات أو روابط صور تخص أضواء الشرق أو أي عميل.

## Legacy — المسار القديم المستبعد من تركيب العميل

الملفان التاليان مثال واضح على سبب عدم تطبيق `supabase/migrations` كاملًا على عميل جديد:

- `20260818135222_staging_app_state.sql` يحتوي سياسة مدير مرتبطة ببريد أضواء الشرق.
- `20260818141102_optimize_app_state_rls.sql` يعيد نفس الارتباط.

وكذلك `20260731090000_customer_portal_resort_info.sql` يحتوي Seed فعلي لأضواء الشرق وروابطه وموقعه.

هذه الملفات لا تُحذف لأنها جزء من تاريخ المشروع واختبارات النسخة الحالية، لكن **لا تدخل في Commercial Install — تركيب العميل التجاري**.

## الحالة الحالية

المسار التجاري **غير مكتمل بعد**. تم تأسيس Core وAdmin foundation وجدول هوية البوابة والصور/Storage فقط.

الخطوة التالية هي نقل جداول Portal المتبقية بالترتيب: التواريخ غير المتاحة، الأسعار، المواسم، التواصل، الميزات النهائية/الملاحظات والنشاط، ثم تشييك العامل. بعد اكتمال السلسلة نضيف Provisioner ونجرب Fresh Install — تركيب من الصفر على Backend معزول.
