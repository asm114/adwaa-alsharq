# Commercial Supabase Migrations — ترحيلات Supabase التجارية

هذا المسار هو المصدر المعتمد مستقبلًا لإنشاء Backend جديد لعميل تجاري. لا تستخدم مجلد `supabase/migrations` القديم كمسار تركيب تلقائي للعميل؛ ذلك المجلد يحتوي تاريخ Staging/أضواء الشرق ويجب اعتباره مرجعًا تاريخيًا حتى يتم ترحيل كل جزء منه إلى المسار التجاري ومراجعته.

## الفصل بين المشروعين

التصميم التجاري الحالي يستخدم Backend منفصلين لكل عميل:

- `core/migrations` لتطبيق الإدارة و`app_state`.
- `portal/migrations` لبوابة العملاء والتشييك والوسائط والجداول العامة.

لا يطبق Migration من مسار Core على Portal أو العكس.

## قاعدة المدير

لا يوجد بريد مطور أو بريد عميل داخل Migration.

بعد تطبيق migrations، يقوم **Provisioner — أداة التجهيز** الآمنة لاحقًا بـ:

1. إنشاء مستخدم Auth للمدير في مشروع العميل.
2. تسجيل UUID المستخدم في `commercial_admins` في Core.
3. إنشاء مستخدم Auth للمدير في Portal وتسجيل UUID في `customer_portal_admins`.
4. إدخال هوية المنشأة وبيانات التواصل والعقد/الشعارات المسموح تخزينها حسب سياسة الأصول.

هذه الخطوات تستخدم بيانات اعتماد إدارية خارج GitHub. يمنع حفظ Service Role Key أو كلمة مرور العميل أو التوقيع/الختم الحقيقي في المستودع العام.

## ما تم في هذه المرحلة

### Core

`20260820001000_core_admin_and_app_state.sql`

- ينشئ جدول عضوية المدير `commercial_admins`.
- ينشئ `is_commercial_admin()`.
- ينشئ `app_state` من الصفر.
- RLS تعتمد UUID المستخدم المصادق عليه، وليس بريدًا ثابتًا.
- لا يزرع بيانات حجوزات أو عملاء أو هوية منشأة.

### Portal

`20260820001000_portal_admin_foundation.sql`

- ينشئ جدول `customer_portal_admins`.
- ينشئ `is_resort_admin()` الذي تعتمد عليه سياسات البوابة.
- لا يحتوي بريدًا ثابتًا.

`20260820002000_portal_property_info.sql`

- ينشئ جدول معلومات المنشأة دون Seed خاص بأضواء الشرق.
- لا يفتح استقبال الحجوزات تلقائيًا قبل إدخال بيانات العميل.
- الهوية الفعلية تدخل في خطوة Provisioning منفصلة.

`20260820003000_portal_images_storage.sql`

- ينشئ جدول معرض الصور وBucket الصور دون أي صورة أو تصنيف خاص بعميل بعينه.
- التصنيفات مرنة ولا تفترض مخطط منشأة محددًا.
- يسمح للجمهور بقراءة Metadata الصور المرئية فقط.
- يسمح للمدير المصادق عليه بإدارة Metadata والرفع والتعديل والحذف.
- Bucket الصور عام لعرض روابط الصور، لكن لا توجد Public SELECT policy على `storage.objects` حتى لا يتحول Storage API إلى فهرس عام للملفات.

`20260820004000_portal_unavailable_periods.sql`

- ينشئ التواريخ غير المتاحة من الصفر دون إغلاقات أو حجوزات Seed.
- يمنع تداخل الفترات وعكس تاريخ البداية والنهاية.
- يضم `source_type` و`booking_id` من أول تركيب لتمييز الإغلاق اليدوي عن الناتج من الحجز.
- يحتفظ بـ`updated_by` لتوافق Admin runtime، مع حجب UUID التدقيق عن anon بواسطة Column Grants — صلاحيات الأعمدة.

`20260820005000_portal_pricing.sql`

- ينشئ جدول أسعار Singleton بقيم `weekday_price` و`weekend_price` المتوافقة مع Portal الحالي.
- يزرع صفًا محايدًا `main` بأسعار صفرية حتى يعمل Fresh Install قبل إدخال أسعار العميل.
- يمنع الأسعار السالبة، ويحجب UUID التدقيق عن anon، ولا يمنح حذفًا روتينيًا لصف الأسعار.

`20260820006000_portal_seasons.sql`

- ينشئ المواسم من الصفر بلا موسم أو سعر Seed.
- يمنع السعر السالب وعكس التواريخ وتداخل المواسم.
- Portal العام يقرأ المواسم الفعالة فقط، وAdmin يدير الكل عبر `is_resort_admin()`.

`20260820007000_portal_contact.sql`

- ينشئ Schema التواصل فقط بدون رقم واتساب أو خرائط أو إنستغرام أو بريد لأي عميل.
- يفرض صيغة رقم واتساب دولية رقمية، وروابط HTTPS، وبريدًا اختياريًا صحيح الصيغة.
- لا يوجد Contact Seed؛ تدخل البيانات عبر Provisioner أو إعداد المدير.

`20260820008000_portal_final_features.sql`

- ينشئ عداد الزيارات بصف `main` صفري محايد، ويخزن فقط SHA-256 لمفتاح الزائر في `private` مع نافذة 24 ساعة؛ لا يخزن المفتاح الخام.
- ينشئ مسار **Feedback — ملاحظات العملاء** بحد 3 محاولات في الساعة لكل مفتاح زائر، ورسالة من 10 إلى 4000 حرف، وبحد أقصى 5 صور.
- يستخدم RPCs محددة `begin_customer_portal_feedback` و`finalize_customer_portal_feedback` بدل فتح INSERT مباشر للعامة.
- ينشئ Bucket خاصًا `customer-portal-feedback` بحجم 5MB وصيغ JPG/PNG/WebP، مع رفع مؤقت مرتبط بتذكرة/رمز قصير العمر؛ القراءة والحذف النهائيان للمدير فقط.
- ينشئ **Activity Log — سجل النشاط** للمدير مع Trigger واحد hardened يستخدم JSON حتى يعمل بأمان مع اختلاف أعمدة جداول Portal.
- سجل النشاط يغطي معلومات المنشأة والصور والتواريخ والأسعار والمواسم والتواصل والملاحظات، ولا ينفذ التسجيل على عمليات الزوار غير الإدارية.
- صفحة `resort/feedback.html` أصبحت تحمل Commercial Config قبل إنشاء Supabase client، و`resort/feedback.js` يقرأ Backend العميل الصريح وNamespace التخزين بدل Project Ref/Publishable Key ثابتين.
- لا توجد بيانات ملاحظات أو عملاء أو اتصالات أو ملفات Seed.

`20260820009000_portal_worker_checks.sql`

- ينشئ **Worker Checks — تشييك العامل** من الصفر داخل Portal Backend التجاري دون أي اسم منشأة أو Project Ref أو بيانات تشغيلية مزروعة.
- ينشئ جدول `customer_portal_worker_checks` وRPCs لإنشاء رابط العامل وقراءة التشييك وتثبيت التقرير، مع SHA-256 للرمز الخام وصلاحية رابط 14 يومًا.
- يمنع أكثر من تشييك نشط للحجز نفسه ويقصر إنشاء/قراءة/تحديث/حذف السجل المباشر على مدير البوابة عبر `is_resort_admin()`.
- يفرض من الخادم 1–6 صور و1–6 اختيارات مرئية، ولا يسمح بجمع `ok` مع أنواع ضرر أخرى.
- ينشئ Bucket خاصًا غير عام `customer-portal-worker-checks` بحجم 8MB، ويسمح للعامل بالرفع فقط داخل مسار التشييك/الرمز الصحيح ما دام التشييك `ready`؛ المدير وحده يقرأ الوسائط ويحذفها بعد التسليم.
- يسمح للعامل بحذف وسائط رفع غير مكتمل فقط أثناء صلاحية الرابط وقبل التثبيت، حتى لا تبقى ملفات مؤقتة بلا حاجة.
- يضم صلاحية حذف السجل للمدير من Fresh Install نفسه بدل الاعتماد على Migration إصلاح لاحق.
- يضيف الجدول إلى `supabase_realtime` لتبقى تنبيهات وصول التقرير متوافقة مع runtime الحالي.

## Legacy — المسار القديم المستبعد من تركيب العميل

الملفان التاليان مثال واضح على سبب عدم تطبيق `supabase/migrations` كاملًا على عميل جديد:

- `20260818135222_staging_app_state.sql` يحتوي سياسة مدير مرتبطة ببريد أضواء الشرق.
- `20260818141102_optimize_app_state_rls.sql` يعيد نفس الارتباط.

وكذلك `20260731090000_customer_portal_resort_info.sql` يحتوي Seed فعلي لأضواء الشرق وروابطه وموقعه.

Migration القديم `20260814114500_customer_portal_unavailable_ownership.sql` يبقى تاريخيًا للنسخة الحالية؛ Fresh Install التجاري لا يحتاجه لأن أعمدة الملكية موجودة من البداية في `20260820004000_portal_unavailable_periods.sql`.

Migrations الأسعار والمواسم والتواصل القديمة تبقى تاريخية للنسخة الحالية. كذلك سلسلة final-features القديمة `20260801010000` و`20260801013000` و`20260801014500` و`20260801020000` تبقى للتاريخ؛ Fresh Install التجاري يستخدم الملف الموحد hardened `20260820008000_portal_final_features.sql` بدل تطبيق الإصلاحات المتتابعة.

Migrations Worker Checks القديمة `20260819054500_customer_portal_worker_checks.sql` و`20260819093000_customer_portal_worker_check_delete.sql` تبقى تاريخية للنسخة الحالية؛ Fresh Install التجاري يستخدم `20260820009000_portal_worker_checks.sql` الذي يجمع الإنشاء والحذف والحماية من البداية بدون Project Ref أو بيانات عميل ثابتة.

هذه الملفات لا تُحذف لأنها جزء من تاريخ المشروع واختبارات النسخة الحالية، لكن **لا تدخل في Commercial Install — تركيب العميل التجاري**.

## الحالة الحالية

اكتمل مخطط Portal التجاري مبدئيًا من ناحية الجداول والـStorage المطلوبة حاليًا: معلومات المنشأة، الصور، التواريخ غير المتاحة، الأسعار، المواسم، التواصل، عداد الزيارات، الملاحظات/النشاط، وتشييك العامل.

الخطوة التالية هي بناء **Provisioner — أداة التجهيز**، ثم تجربة **Fresh Install — تركيب من الصفر** على Backend Core وPortal معزولين. لا يعتبر المسار جاهزًا للبيع النهائي قبل نجاح ذلك الاختبار واختبار ترقية Migration لاحقة.
